# 探店参谋 · 模拟数据设计说明

| 字段 | 内容 |
| --- | --- |
| 产品 | 探店参谋（SpotAide） |
| 范围 | 种子商家、评价、标签、先验选择率；不含真实美团 / 大众点评接口 |
| 生成脚本 | `scripts/seed-data.ts` |
| 表结构 | `prisma/schema.prisma`（Merchant / Review / Tag / 场次与选择） |
| 复现种子 | 固定 `SEED = 20260831` |
| 规模 | 50 家店，每家 20–30 条评价，合计约 1266 条 |

本文说明**为什么用模拟数据、数据长什么样、每条评价怎么造、造完之后产品怎么用**。面试和评审里要分清两件事：库是按真实探店评价的结构造的种子；解析、分析、推荐、记选择这条链路是真的。不得对用户宣称门店真实存在。

---

## 0. 设计目标：数据为决策链路服务，不为刷好评服务

探店参谋的核心不是「再给一页餐厅列表」，而是：听懂口语需求 → 在库存里匹配 → 读评价做语义分析 → 写出可核对的推荐。数据层必须同时满足三件事：

1. **模型有东西可读。** 每家店要有足够长、足够杂的口语句，五维分析、风险信号、原文摘录才站得住。
2. **规则层有信号可拦。** 匹配看标签（安静、包间、太吵），守卫看分析文本（吵、油烟、清淡）。种子必须同时产出标签和互相打架的正文，才能演示「匹配分高、语义却冲突」这件事。
3. **演示可复现、可替换。** 固定随机种子，同一批店名和评价可反复生成；将来换真实评价源时，商家–评价–标签结构不用推倒。

所以种子数据的成功标准不是「看起来像官方榜单」，而是：

- 默认句「带 4 岁小孩，预算 200，想吃粤菜，要有包间」能匹配到粤菜且带包间线索的店。
- 「周末带父母吃饭，要安静有包间」能同时出现安静店和热闹 / 油烟店，方便演示硬需求拦截。
- 分析 Prompt 总能抽出三正三负：每家店都混有好评、中评、差评，而不是全五星。
- 卡片上的评价原文是口语、偶有错别字，观众不会误以为是编辑写的官稿。

明确不做的事：

- 不爬取、不接入美团或大众点评。校招 Demo 没有授权，也不该把真实商户卷进作品。
- 不把 50 家店做成「每家一个完美人设」。真实评价是混杂的；全干净的库反而测不出抽取和拦截。
- 不追求 syntactically 完美的中文。错别字和口头禅是特征，不是缺陷。

## 1. 为什么用模拟数据，而不是真实评价

### 1.1 产品约束

到店决策 Demo 需要「店」和「评价」同时存在。真实平台的评价有版权、隐私、商户授权和接口门槛；两周内独立完成、还要公开部署到 Vercel，接真实源既不合法也不稳定。模拟库把问题收成：在可控文本上，证明链路能读、能拦、能解释。

README 和演示脚本都要求口述同一句话：**评价库是模拟的，链路是真的。** 换真实源时，产品流程（解析 → 确认 → 分析 → 推荐 → 选择）和表结构保持不变，主要替换的是数据质量、时效和去重。

### 1.2 可控对比，比「更真」更适合验收

真实评价的分布不可调：某家店可能连续三个月没有差评，某商圈可能几乎没有粤菜包间。面试要在三分钟里打出：

| 场景 | 种子必须提供的对比 |
| --- | --- |
| 默认演示句 | 粤菜、人均约 200、包间、家庭 / 小孩线索 |
| 硬需求拦截 | 同批候选里既有安静店，也有热闹、油烟、环境分偏低的店 |
| 口味冲突 | 川湘火锅偏辣、粤菜本帮日料偏清淡，正文里也能写出「微辣实际很冲」 |
| 数据不足提示 | 阈值是 5 条；种子每家 20–30 条，主路径不会误触发，规则仍写在产品里 |

这些对比靠菜系配额、正负面模板和标签池预先埋好，而不是指望随机爬来的评价刚好够用。

### 1.3 可复现

`createRng(20260831)` 是线性同余发生器，种子写死。同一台机器重复跑 `scripts/seed-data.ts`，店名、地址、评价条数、情感配比一致（Turso 上已有数据时默认跳过，避免把线上选择记录冲掉；本地会清空后重写）。

这保证：Prompt 回归、`test-pipeline.ts`、演示脚本用的是同一批「白玉粤菜 / 西街湘菜馆」这类名字，而不是每次演示换一批陌生店。

### 1.4 诚实边界

店名是品牌词 + 菜系后缀的虚构组合（如「白玉粤菜」「西街湘菜馆」），地址是上海商圈 + 真实路名 + 随机门牌。路名真实、门店不真实。产品文案、PRD、演示脚本都禁止把它们讲成「上海某家真实餐厅」。

## 2. 领域模型：三张主表，两层用途

### 2.1 表怎么拆

| 对象 | 关键字段 | 给谁用 |
| --- | --- | --- |
| 商家 Merchant | 名称、菜系、人均、地址、商圈、`priorRate`、曝光、选择 | 匹配、卡片、选择率 |
| 评价 Review | 评分 1–5、正文、时间、情感枚举 | 语义分析、原文摘录、先验 |
| 标签 Tag | 挂在单条评价下的短语 | 规则匹配、先验负向占比 |
| 场次 / 曝光 / 选择 | 运行时写入，种子不预填 | 平滑选择率 |

评价正文和标签是**故意分成两路**的：

- **标签**给规则。匹配要在 50 家里快速打分，不能每轮对全文做模型抽取。安静、有包间、太吵、等位久必须是可索引短语。
- **正文**给模型。分析 Prompt 读的是口语段落；守卫后半段也读分析文本里的「吵 / 油烟」，不只信标签。

两路信号可以不一致。例如标签命中了「安静」，中评正文却写「有点吵，聊天要提高音量」。这不是造数失误，而是把真实平台里「标签云和长评打架」的现象做成了可演示的冲突，后面才需要 `recommend-guard`。

### 2.2 运行时怎么读

分析接口取出全部商家，但每家只取**最近 20 条**评价做匹配标签汇总和模型分析。种子每家 20–30 条，因此分析几乎能看到该店的全部近期评价，又给「将来真实源上评价很多」留了截断。评价不足 5 条时 `dataInsufficient` 降权——种子里不会出现，但规则必须存在，换真实源后小店会踩到。

推荐卡片的原文摘录从高分评价里截最多 2 条、每条最多 56 字。所以正面模板不能写太短（低于 8 字会被跳过），也不能只写星级口号。

### 2.3 先验选择率从评价来

写入商家时立刻用评价计算 `priorRate`：

`0.45 × (均分/5) + 0.35 × 好评占比 + 0.2 × (1 − 负面标签占比)`

评价不足 5 条再打 0.7 折，结果限制在 0.05–0.95。展示用选择率再和曝光 / 选择做伪计数平滑。种子因此必须同时有评分、情感、负面标签，不能只造正文。

## 3. 商家怎么铺：规模、地理、菜系、价格

### 3.1 为什么是 50 家，不是 5 家或 500 家

| 规模 | 不行的原因 |
| --- | --- |
| 五六家精品店 | 默认句几乎总能命中，看不出匹配和 Top 5 截断；菜系对比弱 |
| 上百上千家 | 本地 SQLite 种子慢，分析要扫全库打分，Demo 等待变长；也更像在假装已接全量平台 |
| **50 家** | 10 个商圈能轮转、10 个菜系有配额，匹配有区分度；分析只对 Top 5 调模型，延迟可接受 |

每家 **20–30 条**评价：低于约 8 条时五维和三正三负会飘；高于 40 条对 Demo 没有新信息，却增加种子体积和截断前的噪声。20–30 落在「够混杂、又刚好被 take 20 吃进分析」的区间。合计约 1266 条，演示时可以说「五十家店、一千多条评价」，量级清楚。

### 3.2 地理：上海十个商圈

徐家汇、静安寺、五角场、陆家嘴、人民广场、中山公园、虹桥、田子坊、七宝、世纪公园。每商圈三条街道，门牌 18–886 号随机。50 家按 `i % 10` 轮转，保证每个商圈大约 5 家，避免全挤在陆家嘴。

用户说「五角场附近烧烤」或「徐家汇」时，匹配的 location 维有东西可打。商圈名是用户口语里会说的，不是行政区全称。

### 3.3 菜系配额：按探店频次倾斜，不按百科均匀

| 菜系 | 店数 | 人均区间（元） | 店名后缀 | 设计意图 |
| --- | --- | --- | --- | --- |
| 火锅 | 8 | 88–168 | 火锅 | 高频聚餐；可辣可微辣；带父母模板 |
| 川菜 | 7 | 58–128 | 川菜馆 | 辣口主力，和「不要太辣」冲突 |
| 粤菜 | 6 | 98–228 | 粤菜 | 默认演示句主路径；清淡、包间、家庭 |
| 日料 | 6 | 128–268 | 料理 | 约会 / 安静 / 高预算 |
| 烧烤 | 5 | 68–128 | 烧烤 | 商圈 + 今晚类需求 |
| 西餐 | 4 | 158–328 | 餐厅 | 高预算、灯光暗、约会 |
| 本帮菜 | 4 | 88–188 | 本帮菜 | 带长辈、本地风味 |
| 家常菜 | 4 | 48–98 | 小馆 | 低预算、随便吃、停车 |
| 湘菜 | 3 | 3 家即可 | 湘菜馆 | 热闹、香辣，安静需求的反例 |
| 韩餐 | 3 | 78–148 | 韩餐 | 补品类宽度 |

合计必须等于 50，脚本会校验。火锅 / 川菜偏多，是因为本地生活里这类店密度高，也更容易写出「辣度」冲突。粤菜不少于 6 家，避免默认演示句只能命中一两家、看起来像写死推荐。湘菜刻意少：它的角色是反例，不是主力供给。

人均按菜系设上下限，再取偶整数（`roundPrice` 按 2 元对齐），避免出现 137 这种不像价牌的数字。默认句预算 200 会落在粤菜、日料、西餐、部分火锅的区间里，家常菜会被预算维拉开。

### 3.4 店名

50 个不重复品牌词（巷口、白玉、西街、味正、南苑…）与菜系后缀拼接。品牌词先洗牌再分配，同一品牌不会出现两家。名字短、好念、好写进推荐 JSON 的 `merchant` 原名。不要用「第一家店」「某某（分店）」这种模型容易改写的名字。

## 4. 评价分布策略

这是本文的核心。分布不是事后统计出来的，而是生成时按店配出来的。

### 4.1 情感比例：正 : 中 : 负 ≈ 6 : 3 : 1

对每家店的 `reviewCount`（20–30）：

- 负面条数 = `max(1, round(总数 × 0.1))`
- 中性条数 = `round(总数 × 0.3)`
- 正面条数 = 剩余；若算出来小于 1，强制至少 1 条正面
- 再洗牌，避免好评全排在前面

以 20 / 25 / 30 条为例：

| 该店条数 | 正 | 中 | 负 | 约比 |
| --- | --- | --- | --- | --- |
| 20 | 12 | 6 | 2 | 6 : 3 : 1 |
| 25 | 14 | 8 | 3 | 约 5.6 : 3.2 : 1.2 |
| 30 | 18 | 9 | 3 | 6 : 3 : 1 |

全库汇总会落在大约 6:3:1，种子结束时脚本会打印 `positive / neutral / negative` 实数，便于核对。

**为什么不是 8:1:1 或 1:1:1：**

- 真实平台好评偏多。全差评库会让雷达和环境分整体塌掉，默认演示句推不出能上台面的粤菜。
- 但 9:1 的好评墙会让 `risk_signals` 抽成三个「无」，避坑卡片没东西写，商户视角也看不出差评焦点。
- **必须保留约三成中性。** 中评承担「有点吵」「周末人多」「味道中规中矩」这类不极端、却对「要安静」致命的信息。硬需求拦截很多来自中评，而不是 1 星怒评。
- **每家至少 1 条负面。** 避免随机波动下出现「完美店」。分析 Prompt 要求恰好 3 条风险信号，没有差评时模型会编或用「无」凑数。

情感是枚举 `positive | neutral | negative`，和评分绑定、和标签池绑定，不允许「5 星差评」这种自相矛盾（见下一节）。

### 4.2 评分与情感绑定

| 情感 | 评分 | 含义 |
| --- | --- | --- |
| 正面 | 55% 为 5，其余为 4 | 愿意安利，但仍有 4 分空间，避免全员五星 |
| 中性 | 固定 3 | 中评就是 3 星，不漂到 4 或 2 |
| 负面 | 50% 为 2，50% 为 1 | 有「不太值」和「踩坑」两档 |

评分给先验均分、卡片摘录排序、分析 Prompt 的 `[sentiment/rating分]` 前缀。不把评分交给模型去「猜星级」：星级已写在输入里，模型负责语义，不负责再打一个官方分。结果页也写明五维来自评价语义，不是平台星级。

### 4.3 正文：两段拼接 + 口语外壳 + 少量错字

**正面评价**必须带菜系信息。从该菜系的 3 条专用模板里抽 1 条，再从 5 条通用正面（环境、停车、服务、性价比、家庭）里抽 1 条，用逗号拼成一句。这样：

- 粤菜正面会出现白切鸡、蒸点、包间、煲汤、家庭聚餐。
- 湘菜正面会出现口味虾、香辣、热闹聚餐感。
- 通用段保证「停车 / 安静 / 家庭」等匹配标签在正文里也有着落，减少「标签有、原文没有」的空洞引用。

**中性和负面不按菜系分模板。** 从共享池里抽两句不同的，句号拼接。差评写的是等位、分量、服务、油烟、不新鲜、又闷又吵、停车难、微辣实际很冲——这些坑跨菜系都成立。设计后果是：白玉粤菜也可能抽到「油烟味重」「坐里面又闷又吵」。这正是「周末带父母要安静」时，守卫必须读全文、不能只信菜系人设的原因。

**口语外壳每次都加。** 按情感从前后缀里随机各取一条：

| 情感 | 前缀例子 | 后缀例子 |
| --- | --- | --- |
| 正面 | 真的可以啊， / 第二次来了， | 嗯，还会再来。 / 推一个。 |
| 中性 | 说实话， / 一般般吧， | 就这样。 / 看心情吧。 |
| 负面 | 有点无语， / 踩了个坑， | 避雷。 / 慎重。 |

目的是让模型面对的是用户口吻，而不是「环境整洁，服务热情」的电商详情。推荐理由要求「用用户的语言风格」，输入先像用户，输出才不像客服。

**错别字约 18%。** 若正文含有「味道 / 环境 / 推荐 / 特别 / 排队 / 服务 / 不错 / 好吃 / 位置 / 新鲜」，以 0.18 的概率把其中一处换成「味到 / 环镜 / 推见…」。只改一处、只在命中词上改，避免整句不可读。这模拟真实输入法错误，也防止分析 Prompt 只靠关键词精确匹配——「太吵」的近义、错字仍应能进风险信号。

### 4.4 标签：正文命中优先，再从情感池补到 1–3 个

正面池：口味正宗、环境好、适合约会、适合家庭、有包间、停车方便、性价比高、安静、上菜快。

中性池：中规中矩、人多、位置好找、份量一般。

负面池：等位久、分量少、服务差、太吵、性价比低、停车难。

生成顺序：

1. 若正文包含「包间 / 停车 / 约会 / 家庭 / 安静 / 等位 / 太吵」等，先把对应标签放进集合（用 `tag.slice(0, 2)` 或全名去正文里找）。
2. 再随机补到 1–3 个，补丁来自当前情感对应的池。

因此标签**不完全是正文的精确索引**。随机补丁会让部分店带上正文没写死的「有包间」或「太吵」。匹配层可能给高分，分析层读完全文后仍写出热闹 / 油烟。产品选择接受这种噪声：真实标签云也常和长评不一致；规则层 + 模型层双读，比追求种子 100% 对齐更接近上线后的脏数据。

负面标签集合与 `lib/selection-rate.ts` 的 `NEGATIVE_TAG_NAMES` 一致。先验公式用的负向占比，必须和种子池同一套词，否则「停车难」算进评价却算不进先验。

### 4.5 时间

每条评价的 `publishedAt` 落在最近 180 天内，小时 10–21 点（更像用餐后随手写，而不是凌晨刷单）。分析按时间倒序取 20 条，种子的时间抖动让「最近评价」不是同一天复制粘贴。

### 4.6 一条完整评价长什么样（结构示意）

正面粤菜可能是：

第二次来了，白切鸡皮脆肉嫩，蘸料很正，清淡但有味道，适合周末家庭聚餐，小孩也有得吃 推一个。

中性可能是：

说实话，环境一般，有点吵，聊天要提高音量。位置好找，但周末人多，想安静就别这时候来 就这样。

负面可能是：

踩了个坑，油烟味重，衣服上都是，出来还得换衣服的程度。等位太久了，说二十分钟结果快一小时，有点崩 避雷。

评分、情感、标签随这条一起写入。模型看到的是带 `[negative/1分]` 前缀的全文；匹配看到的是标签集合。

## 5. 模板内容如何对齐产品场景

正面模板不是文案装饰，是把演示句和拦截句提前埋进语料。

| 产品场景 | 埋在哪些模板里 |
| --- | --- |
| 带小孩 / 家庭 / 包间 / 粤菜 | 粤菜：「有包间，适合家庭聚餐」；通用正面：「适合周末家庭聚餐，小孩也有得吃」 |
| 带父母、清淡、可微辣 | 火锅：「可以选微辣，带父母来也吃得动，有包间还安静」；川菜：「辣椒用得克制」 |
| 约会、安静 | 日料：「位置靠窗还安静，适合约会」；西餐：「灯光暗、座位疏，说话不用大声」 |
| 停车 | 家常菜：「能停车」；通用：「居然有地下车库」；负面：「停车难到想骂人」 |
| 要安静的反例 | 中性：「有点吵」「周末人多，想安静就别这时候来」；负面：「又闷又吵」「油烟味重」 |
| 要辣 / 不辣 | 湘菜正面香辣过瘾；负面：「辣度标了微辣结果还是很冲，带父母来不太合适」 |

中性池里的「有点吵」是刻意的弱信号：守卫要用能匹配单字「吵」和「油烟」的正则，而不是只认「太吵」。种子先写出这些词，规则才有东西可测。

## 6. 数据如何进入匹配、分析、推荐

把造数和用数放在一张图里，避免「数据设计」停在生成脚本。

```
种子写入
  商家（菜系/价格/商圈）
  评价（评分/正文/时间/情感）
  标签（1–3 个短语）
  priorRate ← 均分 + 好评占比 + 负面标签
        ↓
分析请求
  全库商家 + 每家最近 20 条
  标签并集 → rankMerchants（菜系 0.28 / 预算 0.22 / 包间 0.12 / 口味 0.12 …）
  截 Top 5
        ↓
  对 Top 5 把正文送进评价分析 Prompt（口语 + 错字 + 正负混排）
        ↓
推荐
  规则层读标签分 + 分析文本（吵/油烟/清淡）
  拆 recommendable / ineligible
  模型只在可推荐集合里写理由，原文摘录来自高分评价
```

三层读法不同，所以种子必须同时「像人写的」和「带结构化钩子」：

1. 匹配几乎不读长句，只读菜系、价格、商圈、标签。没有标签池，包间和安静无法稳定进 Top 5。
2. 分析几乎不读标签，只读正文。没有混杂口语句，五维和风险信号会假。
3. 守卫两头都读。没有中评里的「吵」和差评里的「油烟」，拦截演示会退化成只看菜系。

选择率是弱权重 0.06，不能靠把某家店的好评刷到 100% 来操纵排序。种子保持 6:3:1，也是为了不让先验变成第二套「官方分」。

## 7. 刻意保留的「脏」与明确不做的「假」

**保留的脏（接近真实、对产品有用）：**

- 同一家店好评说安静、中评说有点吵。
- 标签随机补丁与正文不完全一致。
- 错别字、口头禅、句号逗号混用。
- 粤菜店也可能抽到油烟差评（负面模板跨菜系）。

**不做的假（会破坏验收）：**

- 不写「本店荣获必吃榜」这类平台腔。
- 不把真实连锁品牌写进店名。
- 不造评价不足 5 条的店来「演示降权」——那会让主路径看起来像故障；降权用规则和单测覆盖。
- 不把 50 家的情感做成全局 6:3:1、单店却全好评。比例是**按店**配的。
- 不在种子里预写推荐理由或五维分数。分数必须现场由模型从正文算出，否则「分析师」叙事不成立。

## 8. 替换真实评价源时，哪些约定要保住

| 约定 | 原因 |
| --- | --- |
| 商家–评价–标签三层 | 匹配、分析、先验都依赖这个拆法 |
| 情感枚举 + 1–5 分 | 先验公式和摘录排序 |
| 标签词表与负面集合对齐 | `NEGATIVE_TAG_NAMES`、匹配关键词 |
| 每店足够多的近期正文 | 分析 take 20；不足 5 条降权 |
| 口语而非官稿 | 模型输入分布应接近线上用户 |
| 重新计算 priorRate | 真实星级和差评结构会变 |
| 产品流程不动 | 解析 / 确认 / 推荐 / 选择与数据源解耦 |

真实源还要补：去重、时效、敏感信息、商户授权。那是上线问题，不是本 Demo 种子的责任。种子的责任是：把结构先做对，把混杂度做到够演示抽取和拦截。

## 9. 复现与核对

```
cd my-demo
./node_modules/.bin/prisma migrate dev
node scripts/seed-data.ts
```

脚本结束会打印商家数、评价总数、标签数、三类情感条数。期望：商家 50；评价约 1000–1500；情感大约 6:3:1；每家都能在库里查到正、中、负。

线上 Turso 已有店时默认不重种，以免清掉真实选择记录。需要重写时才 `FORCE_SEED=1`。

面试可收成四句：

> 没有接美团接口，库是按真实评价结构造的：上海商圈、五十家店、一千多条口语评价，正中负大约六三一，带一点错别字。
>
> 标签给规则匹配，正文给模型分析，两路可以打架，所以后面要硬拦截。
>
> 每家店都混着好评中评差评，不是刷出来的五星墙，分析才能抽出避坑。
>
> 换真实源时换数据、重算先验，产品和模型流程不用推倒。
