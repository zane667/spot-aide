# 探店参谋 · 竞品分析

| 字段 | 内容 |
| --- | --- |
| 产品 | 探店参谋（SpotAide） |
| 对比对象 | 大众点评 AI 能力、小红书笔记推荐、美团小团助手 |
| 口径 | 到店餐饮「已经决定出门吃饭、还没下单」这一段 |
| 结论先行 | 三家分别解决发现、种草、办成事；探店参谋垂直做「对着评价做可拒绝的决策」 |

本文是产品对照，不是行业研报。不比较 DAU、不比较谁模型更大。只回答：用户带着「带 4 岁小孩，预算 200，想吃粤菜，要有包间」走进去，三家各自给他什么，探店参谋作为垂直 Demo 的定位是什么。

先把边界说清：**探店参谋不是要替代这三家。** 点评有真实评价体量和交易，小红书有种草心智，小团有履约和行动代理。本 Demo 没有这些资产。差异化只能落在交互假设和决策机制上：需求先对齐、评价可溯源、硬需求不许圆场、不够就少推。

---

## 0. 用户到底在干什么

到店吃饭前，人通常已经打开过至少一个 App。真正耗时间的不是「世界上有没有店」，而是把模糊约束和互相打架的内容收成一个决定。

这件事可以拆成四步：

| 步骤 | 用户问题 | 常见产品给法 |
| --- | --- | --- |
| 发现 | 附近有什么 | 列表、榜单、信息流 |
| 种草 | 看起来值不值得去 | 笔记、实拍、达人安利 |
| 决策 | 适不适合今晚这顿 | 自己翻评价、自己对照约束 |
| 履约 | 订上、排上、付上 | 预订、团购、排队、外卖 |

三家竞品并不站在同一格：

- **大众点评**：发现 + 海量评价，AI 在把评价变短、把找店变对话；决策仍大量发生在店页的评价流里。
- **小红书**：种草为主，搜索和推荐把人带到「想去」；约束（包间、预算、安静）要用户自己从笔记里抠。
- **小团助手**：美团要把「找」推进到「办」——推荐之后还能订位、下单、打车。

探店参谋只切 **决策** 这一格，而且只切「用评价来决定去哪家」。发现靠种子库里的 50 家店，履约不做。这是范围选择：不做小团的第三层行动代理，把第二层决策辅助做深。

---

## 1. 三家各是什么

### 1.1 大众点评的 AI：在评价帝国上做摘要和找店

大众点评的底盘仍是商户、星级、标签云、按时间 / 评分排序的评价列表，以及必吃榜等内容产品。用户决策习惯是：搜商圈或菜系 → 进店页 → 自己扫评价。

近年 AI 叠在这套底盘上，公开可见的大致有三块：

1. **评价短总结。** 把历史上的长评收成很短的结论，降低「翻 30 条才能形成印象」的成本。张川曾把「找餐厅、点菜」说成点评的长期理想，短总结是先行能力。
2. **点仔一类对话工具**（内测 / 区域推广，含找店帮手、菜品搭配、景点伴游、AI 帮写）。用户一句话需求后，综合评价生成回答，推荐餐厅或点菜，并可接到套餐。形态上已经接近「需求进、方案出」，但仍生长在点评的内容与交易里：目标是帮用户找到店、点到菜、写得出笔记，而不是单独把「硬约束未满足就淘汰」做成主路径。
3. **治理向 AI。** 用智能体打 AIGC 假评、赠品换好评。这解决「评价还能不能信」，和「怎么用评价做今晚的决定」不是同一产品问题。

对探店参谋有启发的：点评证明了评价是到店决策的核心生产资料，AI 摘要有用。仍未从根上换掉的：用户经常是先看到店，再看评价；约束是筛选项或对话里的软匹配，冲突店仍可能出现在推荐里，由人自己判断。

### 1.2 小红书笔记推荐：先让你想去，再让你自己核对

小红书的主交互是双列发现 + 搜索。笔记是第一人称、强视觉、带人设的种草，不是结构化评价库。本地生活上，POI、团购、核销正在把「云种草」往真实到店拉，但用户打开 App 的默认任务仍是：**刷到让我心动的店**，不是 **把包间和预算对完再出门**。

推荐和搜索是两套逻辑：推荐偏兴趣与互动，搜索偏关键词。用户搜「上海粤菜包间亲子」会得到笔记集合，每篇是一个作者的一次体验。要判断「适不适合今晚」，仍需：

- 自己对齐预算、距离、是否还有包间；
- 自己分辨广告、合作、季节性失效；
- 自己决定信哪篇、忽略哪篇。

小红书极擅长激发欲望和提供社会证据（「和我差不多的人去过」）。它不擅长、也不该做成：对同一家店的几十条口碑做五维抽取，再按硬需求闸门淘汰。笔记推荐优化的是完播、互动、核销；探店参谋优化的是「这顿约束有没有被满足」。

### 1.3 小团助手：从帮用户找答案，到帮用户把事办成

小团是美团的本地生活 AI 原生助手。美团把管家能力分成五层：结果准确性、决策辅助、行动代理、情境判断、附加信息提示。2026 年中的升级重点落在第三层：授权确认后协助订位、下单、打车；没接线上预订的店还可以 AI 外呼。

公开案例很典型：「公司附近、6 个人、晚上 7 点能订上的川菜」——距离、营业、评价、余位一起筛，确认后去订。这已经覆盖探店参谋想解决的那句话的前半（理解需求）和后半之外的履约。

小团能这么做，靠的是全国商家、评价、交易、余位和履约网络，不是 Prompt 写得更长。探店参谋作为可演示 MVP，既没有这些接口，也不假装有。对齐方式不是「也做订位」，而是：**小团要办成事，前面必须有一次靠得住的决策；本产品把决策这一刀切深，做成可演示的机制。**

商户侧美团另有 CatPaw。探店参谋的「商户视角」是同一份评价换角色读，只是切片对标，不是商家工作台。

## 2. 一张表看完差异

| 维度 | 大众点评 AI | 小红书笔记推荐 | 小团助手 | 探店参谋 |
| --- | --- | --- | --- | --- |
| 用户任务 | 找店、看口碑、点菜、写评 | 被种草、搜体验、决定想去 | 找 + 比 + 办（订/下单/车） | 对着评价决定去哪家 |
| 默认入口 | 搜店 / 店页 / 对话找店 | 发现页 / 搜索笔记 | 对话管家 | 一句话需求 |
| 内容单元 | 评价、星级、榜单、摘要 | 单篇笔记 | 平台供给 + 评价 + 实时余位 | 库存评价 + 标签 |
| 需求怎么进 | 筛选项或对话 | 关键词、兴趣画像 | 自然语言任务 | 口语 → 可改标签 |
| 约束怎么处理 | 软筛选，人最终判断 | 人从笔记里自己抠 | 结合实时供给筛选 | 规则硬拦截，不够就少推 |
| 输出 | 店列表 / 短总结 / 点菜建议 | 笔记流 | 方案 + 可执行动作 | Top 1–3 + 理由 + 原文 + 避坑 + gap |
| 失败时 | 仍有列表可翻 | 换一篇笔记 | 执行失败或改方案 | 明确写差距，禁止圆场 |
| 模型角色 | 摘要、对话推荐、治理 | 分发与理解（平台侧） | 管家 + 行动代理 | 分析师，不当闸门 |
| 履约 | 套餐 / 预订（平台能力） | 团购核销 | 核心能力 | 不做 |
| 数据 | 海量真实评价 | UGC 笔记 | 评价 + 交易 + 履约 | 模拟种子，链路为真 |

一句话对照：

- 点评 AI：**把已有评价变好用**，人还在店和列表之间。
- 小红书：**把「想去」做出来**，核对留给人。
- 小团：**把「去成」做出来**，决策是管家里的一环。
- 探店参谋：**把「该不该去、凭什么」做成主路径**，去不成也要说清楚。

## 3. 和每一家比，差在哪一步

### 3.1 相对大众点评：从「先看见店」到「先对齐需求」

点评即使用上短总结和点仔，主心智仍是内容场：先有店，再有评价，AI 帮忙读得快一点。探店参谋把顺序反过来——先产出结构化标签（场景、预算、菜系、口味、氛围、设施），用户确认或改完，再进库存匹配。没对齐需求，不生成有效推荐。

第二点是 **可拒绝**。点评推荐和列表的产品惯性是「总要给你几家」。探店参谋允许只出 1 家，并把热闹、油烟店写进 gap，而不是写「虽然吵但也能安静吃」。这是规则层闸门，不是把「请诚实」写进 Prompt 了事。

第三点是 **溯源形态**。点评摘要追求短和全；探店参谋每张卡强制绑定理由、评价原文摘录、五维雷达（标明来自语义而非官方星级）、避坑。短不是目标，可核对才是。

不声称：摘要质量、召回、防假评。那些是点评的主战场，Demo 没有资格赢。

### 3.2 相对小红书：从「一篇体验」到「一家店的口碑集合」

小红书的决策单元是笔记。一篇写得好，就可以让人今晚出门；一篇是广告，也可以让人踩坑。探店参谋的决策单元是 **商家 + 其评价集合**。模型必须读同一家店里好坏混杂的句子，抽出三正三负，而不是认准最会拍的作者。

约束上，小红书靠搜「亲子粤菜包间」碰运气；探店参谋把包间、安静、辣度写成硬需求，标签匹配高但正文喊吵的店会被拦下。种草解决「好不好看、好不好拍」；这里解决「今晚这几个条件能不能同时成立」。

不声称：内容生态、同城流量、种草转化。探店参谋没有笔记，也不做发现页。

### 3.3 相对小团：同一战略方向上的垂直切片，而不是缩小版小团

小团要覆盖本地生活任务闭环，餐饮只是其中一类；探店参谋只做餐饮到店决策。小团升级的叙事是「问」变「帮」；探店参谋停在「帮你看清楚，然后按一下我就去这家」。

关键差异不在功能多少，而在 **决策机制是否暴露**：

| 机制 | 小团（公开描述） | 探店参谋（可演示） |
| --- | --- | --- |
| 需求结构化 | 对话里理解 | 标签页，用户可改，改完才分析 |
| 硬约束 | 结合余位等实时条件筛 | 包间 / 安静 / 菜系 / 辣度规则拦截，单测可回归 |
| 解释 | 方案说明 | 原文 + 雷达 + 避坑 + gap |
| 采纳 | 订位 / 下单 | 「我就去这家」，记曝光和选择率 |
| 双端 | C 端管家；B 端另有 CatPaw | 同一条评价，结果页切商户视角 |

不做订位，是因为没有真实供给和履约，做了是假的；把假履约做进 Demo，会把「分析师」叙事冲掉。小团的行动代理依赖平台履约网络，不是本 Demo 的范围。

相对小团已能推荐川菜：小团要在全国任务上通用，决策细节容易被「办成」吸走。探店参谋把「评价语义 vs 用户硬需求」做成主界面冲突——匹配分高但油烟店被拿掉、只推 1 家——验证的是闸门，而不是聊天是否流畅。

## 4. 探店参谋的差异化

1. **需求驱动，且需求可改。** 不是筛选项，也不是一次性对话。解析错了可以在确认页改标签，后续分析用改后的条件。这承认模型会拆错，把纠错权给人。
2. **LLM 当分析师，规则当闸门。** 理由、五维、避坑由模型写；包间、安静、菜系、辣度冲突由代码剔除。Prompt 迭代里记录过圆场失败：只改 Prompt 不够，配额会逼模型凑满 Top 3。
3. **推荐必须可拒绝、可核对。** 数量随可推荐集合收缩；gap 比列表更诚实；原文摘录来自库存评价，追问禁止编菜单。
4. **闭环停在选择，不停在文案。** 「我就去这家」写下本轮去向，选择率进入弱匹配。验证的是有没有人肯点，不是理由好不好看。商户视角用同一份分析换角色，对应美团 C + B 双端，但不假装做成 CatPaw。

这四条加在一起，针对的是同一痛点：**评价看不完，约束对不齐，推荐爱圆场。** 点评用摘要减轻「看不完」；小红书用种草绕开「对不齐」；小团用履约缩短「决定以后怎么办」。探店参谋把「对不齐 + 爱圆场」拉到台面上做成功能。

---

## 5. 明确不竞争的三件事

写竞品分析最容易膨胀的，是把 Demo 写成「下一代超级 App」。下面三件主动放弃：

1. **不拼数据真实与规模。** 50 家模拟店、约 1266 条口语评价。评价库是模拟的，解析 / 分析 / 推荐 / 选择是真的。换真实源时结构可复用。
2. **不拼行动代理。** 没有订位、排队、支付、外呼。感谢页只表示「你选了这家」，不假装已下单。
3. **不拼内容生态。** 不做笔记、不做达人、不做关注流。发现和种草交给点评与小红书。

放弃之后，留下的是：AI 放在什么位置、如何处理幻觉和冲突、主路径的产品逻辑是否闭环。

---

## 6. 结论

点评和小红书分别用评价摘要和笔记种草降低「看不完 / 被种草」的成本，用户仍要自己把「包间、安静、预算」对到店上。小团把「找」推进到「办」，决策是管家里的一环。

探店参谋做的是决策辅助这一层的垂直 Demo：先把今晚怎么吃收成可改标签；再只对库存评价分析；硬需求冲突的店不准靠文案圆进来；最后用「我就去这家」记下选择。

不做订位，是因为没有履约数据。差异化不在功能更多，而在 **需求先对齐、评价可溯源、推荐可拒绝**。
