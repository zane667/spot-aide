# 探店参谋 · 核心 Prompt 迭代说明

| 字段 | 内容 |
| --- | --- |
| 产品 | 探店参谋（SpotAide） |
| 范围 | 三条线上主路径 Prompt：需求解析、评价语义分析、推荐生成 |
| 模型 | DeepSeek `deepseek-v4-flash`，统一走 `lib/deepseek.ts` |
| 终版位置 | `lib/prompts.ts`（仓库里只保留线上版本，历史版本写在本文） |
| 配套校验 | `lib/schemas.ts`（zod `.strict()`） |
| 规则兜底 | `lib/recommend-guard.ts`（硬需求拦截，Prompt 3 必须一起看） |
| 测试 | `scripts/test-prompts.ts`（20 条需求）+ `scripts/test-pipeline.ts`（全链路）+ `lib/recommend-guard.test.ts` |

本文记录三条核心 Prompt **怎么改到能过验收**。每一条都按同一结构写：初始版本 → 遇到的问题（带用例和典型输出）→ 优化方案 → 再测标准 → 最终版本。原则是：

- 最短 Prompt 先跑通，证明链路可走。
- 每一轮只改一类问题，不把格式、空值、圆场混在一次修改里。
- JSON 过不了 zod 就算失败，不允许「差不多就展示」。
- 推荐不要把「拦截」全交给模型：规则层先拆成可推荐 / 不可推荐，Prompt 只负责在可推荐集合里写理由。

追问 Prompt（Prompt 4）是结果页能力，不在这三条主路径里。文末只作对照，不展开迭代。

固定测试句贯穿全程：

- 主路径用例：「带 4 岁小孩，预算 200，想吃粤菜，要有包间」
- 收紧硬需求时用：「周末带父母吃饭，要安静有包间」

---

## 0. 总原则：为什么不一次写很长

立项时三条 Prompt 都很短：角色 + 任务 +「请输出 JSON」。这能证明「模型能抽标签、能打分、能写理由」，但上线不够用。联调里反复出现的不是「模型不够聪明」，而是三类工程问题：

1. **格式不稳。** markdown 代码块、中文键、嵌套对象、`crowd` 写成 `"4人"`，zod 直接打回，确认页和雷达图读不到字段。
2. **字段乱编。** 用户没提的预算、菜系被补上；空输入、单字「吃」仍给出完整标签。确认页会亮出一排用户根本没说过的东西，伤害信任。
3. **推荐会圆场。** 硬需求（安静、包间、辣）对不上，仍凑满 Top 3，理由写成「虽然吵但也能安静吃」。用户看到的是互相打架的文案：卡片在推，注意事项又在劝退。

所以迭代策略固定成四件事：

- Prompt 里**锁死 JSON 形状**（键名、null、数组长度、禁止 markdown）。
- 调用侧开 `response_format: json_object`，并关掉思考模式，避免超时和空转。DeepSeek 的 JSON 模式要求 Prompt 里也写明只输出 JSON，否则可能返回空对象。
- 推荐不要指望模型当闸门：规则层先拆成 `recommendable` / `ineligible`，Prompt 只在可推荐集合里写。
- 用同一批测试句回归。解析用 20 条覆盖常规 / 模糊 / 空字段 / 极端预算；推荐用「安静有包间」专门打圆场。

三条 Prompt 的职责边界也要先说清，后面改词才不会越改越长：

| Prompt | 输入 | 输出 | 不负责的事 |
| --- | --- | --- | --- |
| 需求解析 | 用户一句话 | 九个标签 + `inference` | 用户改标签（确认页）、商家匹配 |
| 评价分析 | 同一家店的多条评价 | 五维分数 + 三正三负 + 适不适用 | 跨店比较、推荐排序 |
| 推荐生成 | 需求标签 + 已分析的候选 | 最多 3 条理由 / 避坑 + `gap` | 硬需求拦截（规则层）、匹配打分 |

## 1. Prompt 1：需求解析

**任务：** 用户一句话 → 结构化标签，供确认页展示、修改，并作为后续匹配输入。

**接口：** `POST /api/parse`。成功后进入确认页；用户改完的标签才进分析和推荐，所以这一步允许「第一稿不够准」，但不允许「编造用户没说过的槽位」。

**固定对照句：**

| 编号 | 类型 | 输入 | 用来验什么 |
| --- | --- | --- | --- |
| 01 | 常规 | 带4岁小孩，预算200，想吃粤菜，要有包间 | 多槽位同时命中；budget / crowd 类型 |
| 02 | 常规 | 周末约会，要安静，人均150到200 | 区间预算、氛围 |
| 16 | 空字段 | （空字符串） | 不得编造标签 |
| 17 | 空字段 | 吃 | 无意义输入与空串同等处理 |
| 11 | 模糊 | 一个人随便吃 | 只推断说得出口的（独食），菜系预算保持 null |

### 1.1 初始版本（V1）

当时只写角色、九个维度和两句约束，没有给出 JSON 样例。目标是「模型知道要抽哪些槽位」，能证明链路可通：

```
你是一个本地生活消费场景的需求解析助手。你的任务是将用户用自然语言描述的到店消费需求，解析为结构化的标签。

解析维度：
- scene: 场景（聚餐/约会/商务/家庭/独食/团建）
- budget: 人均预算（数字范围，单位：元）
- cuisine: 菜系偏好（中餐/日料/西餐/火锅/烧烤...）
- taste: 口味约束（不辣/偏甜/清淡...）
- atmosphere: 氛围要求（安静/热闹/浪漫/私密...）
- facility: 设施要求（包间/停车/WiFi/无障碍...）
- crowd: 人数（数字）
- time: 时间约束（工作日/周末/午餐/晚餐）
- location: 位置偏好（商圈/地铁站附近）

输出JSON格式，每个字段如果用户未提及则填null。
对模糊表述做合理推断，但必须在"inference"字段说明推断依据。

用户需求：
{query}
```

这一版的问题不在「维度列错了」——九个槽位后来几乎没改——而在约束太软：「输出 JSON 格式」不等于「输出且仅输出这一份对象」。

### 1.2 遇到的问题

**现象 A：不是合法 JSON，或包在 markdown 里。**

模型常在 JSON 前后加客套话，或包一层代码围栏。典型返回类似：

好的，解析结果如下：

（json 代码块）`{ "scene": "家庭聚餐", "budget": 200 }`

`chatJSON` 按 JSON 解析会失败。即便剥掉围栏，`budget` 有时是数字有时是字符串，后续确认页和匹配对不齐。DeepSeek 开了 JSON 模式之后，客套话少了很多，但若不在 Prompt 里写明「不要 markdown、不要其它字段」，仍会出现 ````json` 包裹或多余说明字段。

**现象 B：类型漂、多字段。**

用例 01「带 4 岁小孩，预算 200，想吃粤菜，要有包间」在 V1 下不稳定：

| 字段 | 产品期望 | V1 常见返回 | 后果 |
| --- | --- | --- | --- |
| crowd | 整数或 null | `"4人"` / `"一家四口"` | zod 要 `number \| null`，整次解析失败 |
| budget | 字符串 `"200"` | `200`（number）或 `"200元"` | 匹配里的区间解析对不上 |
| 额外键 | 不允许 | `child`、`notes`、`kids` | `.strict()` 打回；若当时没 strict 会静默进下游 |

「带 4 岁小孩」本身就不该被硬填成 crowd=4。小孩是场景线索，不是用餐人数。正确做法是 crowd 保持 null（用户没说几个人吃饭），在 `inference` 里写「提到 4 岁小孩，推断家庭场景」。V1 没有这条边界，模型两种都干过：写成 4，或发明 `has_child: true`。

**现象 C：空输入仍「很勤奋」。**

用例 16 空字符串、用例 17「吃」：V1 仍给出 scene=聚餐、budget=`"100-200"` 一类默认值。`inference` 有时缺失、有时写「用户想吃饭」。确认页会亮出一排用户根本没说过的标签。产品上这比解析失败更糟：失败至少能提示重说，编造会让用户以为系统擅自替他做了决定。

**现象 D：过度推断。**

「一个人随便吃」被补上具体菜系（例如「家常菜」）或商圈。产品要求：没说的必须是 null，推断只允许写在 `inference` 里，并且确认页可以改。V1 把推断写进了业务字段，用户在确认页看到的是「系统已经替我选好了菜系」，而不是「系统猜我是独食，菜系还空着」。

### 1.3 优化方案

只改「格式与空值」这一类问题，不在这一轮去优化匹配权重：

1. Prompt 内嵌**唯一合法 JSON 骨架**，声明「不要其它字段、不要 markdown」。键名、类型、null 都写在字面量里，不再只在列表里用中文解释。
2. 逐条写类型：`budget` 用 `"200"` / `"150-200"`；`crowd` 必须是数字或 null，禁止 `"4人"`。
3. `inference` 改为必填非空：有推断写依据，空输入写原因。这样空输入也有合法 JSON，不会因为缺字段失败。
4. 明确空串和无意义输入：除 `inference` 外全部 null。把「吃」写进 Prompt，作为反例，避免模型把它当成「想吃饭 → 聚餐」。
5. 调用侧：`response_format: json_object`；user 再补一句「请严格按 System Prompt 输出 JSON」。
6. 产品侧：`parseNeedSchema` 用 zod `.strict()`，多字段直接失败，不静默丢弃。`crowd` 只接受整数或 null。

改动的句子可以概括成：从「输出 JSON 格式」换成「输出必须是且仅是如下 JSON」，并补上五条规则。维度列表本身几乎没动，说明问题不在「槽位设计」，而在「输出契约」。

配套的 user 消息很短，不把规则再写一遍，避免 system / user 两套说法打架：

```
请严格按 System Prompt 输出 JSON。
```

### 1.4 再测

用 `scripts/test-prompts.ts --only=parse` 跑 20 条。通过标准：**解析结果必须通过 `parseNeedSchema`**，否则记失败并打印原文。不接受「八个字段对了、crowd 写成字符串就算及格」。

预期（人工抽查，不是每条都写死标准答案，因为模型对 scene 用词会有合理浮动）：

- 01：budget 为字符串 `"200"` 或等价；facility 含包间；cuisine 含粤菜；crowd 为数字或 null（提到小孩不等于 4 人）；未提的 taste / location 为 null；inference 非空。
- 02：atmosphere 含安静；budget 为 `"150-200"` 一类字符串；time 含周末。
- 16 / 17：标签全 null，`inference` 说明无法解析或信息不足。
- 11：scene 可为独食，菜系 / 预算 / 设施保持 null。
- 18 / 19 / 20：极端预算仍要输出字符串，不要改成「无预算」之类自由发挥字段。

### 1.5 最终版本

见 `PARSE_NEED_SYSTEM`。相对 V1 增加了 JSON 字面量、五条硬规则，以及运行时占位 `{query}`。

```
你是一个本地生活消费场景的需求解析助手。你的任务是将用户用自然语言描述的到店消费需求，解析为结构化的标签。

解析维度：
- scene: 场景（聚餐/约会/商务/家庭/独食/团建）
- budget: 人均预算（数字范围，单位：元）
- cuisine: 菜系偏好（中餐/日料/西餐/火锅/烧烤...）
- taste: 口味约束（不辣/偏甜/清淡...）
- atmosphere: 氛围要求（安静/热闹/浪漫/私密...）
- facility: 设施要求（包间/停车/WiFi/无障碍...）
- crowd: 人数（数字）
- time: 时间约束（工作日/周末/午餐/晚餐）
- location: 位置偏好（商圈/地铁站附近）

输出必须是且仅是如下 JSON（不要其它字段、不要 markdown）：
{
  "scene": string | null,
  "budget": string | null,
  "cuisine": string | null,
  "taste": string | null,
  "atmosphere": string | null,
  "facility": string | null,
  "crowd": number | null,
  "time": string | null,
  "location": string | null,
  "inference": string
}

规则：
- 用户未提及的字段填 null，不要编造。
- budget 用字符串，如 "200" 或 "150-200"；未提及则 null。
- crowd 必须是数字或 null，不要写成字符串。
- inference 必须是非空字符串：有推断就写依据，空输入/无法解析就写明原因。
- 空字符串或无意义输入（如「吃」）时，除 inference 外全部为 null。

用户需求：
{query}
```

**仍交给产品、不交给 Prompt 的事：** 用户可在确认页改标签。Prompt 负责「拆对第一稿」，不负责交互修正。匹配权重、选择率也不在这一步。

**V1 → 终版对照：**

| 点 | V1 | 终版 |
| --- | --- | --- |
| 输出约定 | 「输出 JSON 格式」 | 内嵌唯一骨架 + 「不要其它字段、不要 markdown」 |
| budget | 「数字范围」 | 字符串 `"200"` / `"150-200"` |
| crowd | 「数字」但未禁字符串 | 必须是 number 或 null |
| 空输入 | 未写 | 除 inference 外全 null，并举「吃」为反例 |
| inference | 「必须说明」但未要求非空 | 必填非空字符串 |
| 运行时校验 | 无（后补） | `parseNeedSchema.strict()` |

## 2. Prompt 2：评价语义分析

**任务：** 同一家店的多条评价 → 五维分数 + 三个正面标签 + 三个风险信号 + 适不适用场景。结果进雷达图、商户视角，也作为推荐上下文。

**接口：** `POST /api/analyze` 按候选店循环调用。商户洞察复用同一 Prompt，不再单独养一套分析词，避免 C 端雷达和 B 端洞察说两套话。

**测试方式：** 种子库取 3 家店、每家约 8 条最近评价，跑 `test-prompts.ts --only=analyze`。schema 为 `analyzeInsightSchema`：五维 1–10 整数，`top_tags` / `risk_signals` 长度必须恰好为 3。

### 2.1 初始版本（V1）

```
你是一个餐饮评价分析专家。请对以下用户评价进行多维度语义分析。

分析维度（每个维度1-10分）：
1. 口味质量（食材新鲜度、味道层次、出品稳定性）
2. 环境体验（装修、噪音、座位舒适度、卫生）
3. 服务质量（响应速度、态度、专业度）
4. 性价比（价格与品质的匹配度、分量）
5. 场景适配度（适合哪些消费场景）

同时提取：
- top_tags: 最突出的3个正面标签
- risk_signals: 最突出的3个负面风险信号
- best_for: 最适合的消费场景
- avoid_if: 什么情况下不推荐

输出严格的JSON格式。

用户评价：
{reviews}
```

问题在「严格」没有形状：维度是中文序号，键名只出现在「同时提取」里，分数怎么放完全没说。模型可以「严格」地返回一份我们读不懂的 JSON。

### 2.2 遇到的问题

**现象 A：分数嵌套或中文键。**

产品读的是扁平英文键：`taste_quality` / `environment` / `service` / `value` / `scene_fit`。V1 常见三种走样：

1. 中文键：`"口味质量": 8`
2. 嵌套：`"dimensions": { "taste": { "score": 8, "comment": "不错" } }`
3. 混用：顶层既有中文又有 `top_tags`

雷达图读不到键，分析被置为 `null`，卡片上五维空洞。更糟的是推荐 Prompt 会拿到「有店、无分析」，后面只能靠错误信息或跳过，理由写不具体。

**现象 B：数组长度飘。**

Prompt 写了「最突出的 3 个」，但没有「必须恰好 3 条非空」。模型会：

- 给 5 个正面标签（想表现全面）
- 负面只有 1 个或空数组（种子里某家店偏正面时尤其明显）
- 用 `"无"` / `"暂无"` 凑数，zod 的 `min(1)` 能过，但产品展示会出三个「无」

产品要稳定三正三负，方便卡片和商户视角对齐。zod `.length(3)` 直接失败，逼 Prompt 把长度写死。

**现象 C：一次分析多家店。**

V1 写「对以下用户评价」，没写「同一家店」。测试脚本早期曾把多家店的评价拼进同一段 user 内容，模型就返回数组：

`[{ "merchant": "白玉粤菜", "taste_quality": 8 }, { "merchant": "西街湘菜馆", "taste_quality": 7 }]`

线上接口是**按店循环调用**的，外层数组无法对应 `analyzeInsightSchema`。即便后来输入改成单店，Prompt 若不写「不要输出数组或多商家结构」，模型仍可能自我发挥成列表。

**现象 D：分数不是 1–10 整数。** 出现 8.5、`"高"`、0、11、`"8/10"`。雷达和守卫里的环境分阈值（安静时环境分必须 ≥ 7）都依赖整数，小数会让比较变得含糊。

### 2.3 优化方案

这一轮只锁「单店 + 扁平英文键 + 长度」，不在 Prompt 里教模型「怎么打分才客观」——那会把 Prompt 写成评分手册，且很难回归。

1. 标题改为「以下同一家店的用户评价」。
2. 给出完整 JSON 字面量，五个分数都在顶层英文键，禁止嵌套 `dimensions`。
3. 规则写死：1–10 整数、`top_tags` / `risk_signals` 恰好 3 条非空字符串、不要按店名分组、不要输出数组。
4. 输入用 `{reviews}` 拼成「商家名 + 序号评价」，降低模型自己发明店名的机会。
5. 单店分析失败时，该店 `analysis` 置空并带 error，**不拿假分数填雷达**。宁缺毋滥。

输入拼装示例（示意，不是 Prompt 正文）：

```
白玉粤菜
1. [正面/5分] 环境安静，有包间，适合带老人
2. [负面/2分] 周末要排队
...
```

### 2.4 再测

3 家种子店应全部通过 `analyzeInsightSchema`。人工抽一眼：

- `risk_signals` 应能对上种子里的负面标签（等位久、太吵、停车难等），而不是三个「无」。
- 环境分要能区分「安静粤菜」和「热闹湘菜」，后面 Prompt 3 的守卫才有信号可用。
- 同一家店连续跑两次，键名必须稳定；分数允许 ±1 波动，不允许键结构变化。

商户视角复用同一 Prompt：C 端雷达和 B 端「顾客在意什么」来自同一份 JSON，只是展示不同。

### 2.5 最终版本

```
你是一个餐饮评价分析专家。请对以下同一家店的用户评价进行多维度语义分析。

分析维度（每个维度1-10分）：
1. 口味质量（食材新鲜度、味道层次、出品稳定性）
2. 环境体验（装修、噪音、座位舒适度、卫生）
3. 服务质量（响应速度、态度、专业度）
4. 性价比（价格与品质的匹配度、分量）
5. 场景适配度（适合哪些消费场景）

同时提取：
- top_tags: 最突出的3个正面标签
- risk_signals: 最突出的3个负面风险信号
- best_for: 最适合的消费场景
- avoid_if: 什么情况下不推荐

输出必须是且仅是如下 JSON（不要其它字段、不要按店名分组、不要 markdown）：
{
  "taste_quality": number,
  "environment": number,
  "service": number,
  "value": number,
  "scene_fit": number,
  "top_tags": [string, string, string],
  "risk_signals": [string, string, string],
  "best_for": string,
  "avoid_if": string
}

规则：
- 五个分数必须是 1 到 10 的整数，放在上述英文键下，不要嵌套对象。
- top_tags 与 risk_signals 必须恰好 3 条非空字符串。
- 只分析这一家店，不要输出数组或多商家结构。

用户评价：
{reviews}
```

**Prompt 解决不了、交给规则的部分：** 评价不足 5 条时 `dataInsufficient` 降权，并在卡片提示「仅供参考」。这是业务规则，不写进分析 Prompt，避免模型自己发明「数据充足」。分析 Prompt 只对「眼前这几条评价」负责，不判断样本量是否够做决策。

**V1 → 终版对照：**

| 点 | V1 | 终版 |
| --- | --- | --- |
| 分析对象 | 「以下用户评价」 | 「以下同一家店的用户评价」 |
| 分数键 | 中文序号，未规定英文键 | 五个顶层英文键 |
| 数组 | 「最突出的 3 个」 | 恰好 3 条非空 |
| 结构 | 「输出严格的 JSON」 | 禁止分组、禁止数组、禁止嵌套 |
| 失败策略 | 未写 | 单店失败 analysis=null，不填假分 |

## 3. Prompt 3：推荐生成

**任务：** 在已经匹配、已经分析过的候选上，生成最多 3 条推荐理由和避坑，并在硬需求有缺口时写 `gap`。

这是三条里改得最多的一条。因为格式稳定之后，**产品失败出在「会说话但在圆场」**——卡片能出、JSON 能过、用户却看到「要安静」下面推了一家热闹店。

**接口：** `POST /api/recommend`，SSE 流式输出。拼完正文后再过 `recommendResultSchema`，长度 1–3，`.strict()`。

### 3.1 初始版本（V1）

```
你是一个本地生活推荐顾问。基于以下信息：
- 用户需求标签：{user_needs}
- 候选商家评价分析结果：{merchant_analyses}

请生成推荐方案：
1. 按匹配度排序，推荐Top 3商家
2. 每个商家给出"推荐理由"（用自然语言，要具体、有说服力）
3. 每个商家给出"注意事项"（避坑提醒）
4. 如果所有商家都不完全满足需求，说明差距在哪里

注意：
- 推荐理由必须基于评价数据，不要编造
- 如果某个维度数据不足，明确标注"该维度数据不足，建议实地体验确认"
- 用用户的语言风格回应，不要过于正式
```

V1 默认「一定有 Top 3」，差距只是第 4 点口头说明，没有 JSON 字段，也没有「不准把冲突店写进列表」。`{merchant_analyses}` 当时是候选数组一股脑塞进去，模型同时看到可推和不可推的店，很容易「各打五十大板」：列表里推，gap 里又承认不行。

### 3.2 第一轮：格式（V1 → V2）

**遇到的问题。** 返回散文、或 `recommendations` 里用 `name` / `why`、或缺少 `notes`、或把 gap 做成数组 / 对象。SSE 拼完后无法过 schema，结果页卡在「生成中」或报错。

**优化方案。** 锁 JSON，其它句子先不动：

```
{
  "recommendations": [
    { "merchant": string, "reason": string, "notes": string }
  ],
  "gap": string | null
}
```

并规定 `merchant` 必须用候选原名（不能写「第一家粤菜店」）。`recommendResultSchema` 长度 1–3，字段 `.strict()`。

**再测。** `test-prompts.ts` 与全链路 SSE 拼完正文后必须通过 schema。这一轮只要求「能解析、能上卡」，不验收推荐质量。过了这一关，后面才能看见圆场——因为圆场的 JSON 往往是合法的。

### 3.3 第二轮：圆场与凑数（V2 → V3）

格式过了之后，用「周末带父母吃饭，要安静有包间」跑全链路，质量仍差。下面三轮是真实联调复盘，店名为种子库内名称。问题点是真的；具体 reason 措辞按当时输出意译，不把一次抽样当成永远不变的标准答案。

**输入：** 周末带父母吃饭，要安静有包间（未指定菜系和预算）。

**第 1 次联调。**

| 排序 | 店 | 问题 |
| --- | --- | --- |
| #1 | 白玉粤菜 | 相对可接受：家庭、清淡、环境 |
| #2 | 南苑小馆 | 理由写成「老板人好、米饭管够」，与安静 / 包间无关 |
| #3 | 西街湘菜馆 | 自己写「氛围热闹、父母喜欢安静就不合适」，却仍在推荐列表里 |

`gap` 往往比列表诚实：承认候选普遍没坐实安静和包间。也就是说**模型知道冲突，但「推荐 Top 3」更像硬指标**，于是把不该推的店填进去。产品表现是：用户先看到三张漂亮卡片，再在底部看到「其实都不太安静」——决策被文案拆成两半。

这一轮的匹配侧也有责任：安静 / 包间在种子标签里经常命中，匹配分可以很高，热闹店仍能进 Top 5 候选。Prompt 看见的已经是「高分候选」，更容易把它们写成推荐。

**第 2 次联调（只收紧 Prompt 用语，守卫还很窄）。**

西街不再进 Top 3，但 **味正料理** 出现「油烟味和吵」紧接着「仍能满足安静吃饭」——这是产品明确要禁的句式。守卫当时只认「太吵|嘈杂|热闹|吵闹」，认不出「有点吵」「油烟」；环境分要很低才剔除。模型仍能看到冲突店的完整分析，并自行改口。

这说明：**只改 Prompt 不够。** 模型只要在上下文里看见那家店，就有动机把它写进配额。配额是 3，可推荐若按模型自己的标准也是 3，冲突店就会被圆进来。

**第 3 次联调（Prompt + 规则一起改）。**

结果：只推荐白玉粤菜 1 家；味正、南苑、西街只出现在 gap。理由不再出现「虽然吵 / 油烟，但能满足安静」。

### 3.4 原因拆开看

不是「模型不听话」一件事，是四件事叠在一起：

1. Prompt 写「推荐 Top 3」，模型把 3 当成必须凑满的配额。少推荐在它看来像没完成任务。
2. 候选是匹配 Top 5。标签命中可以很高，但分析文本里仍有「吵」「油烟」。匹配分和语义分析说的不是同一件事。
3. 只改 Prompt 时，模型仍能看到冲突店的完整分析（分数、标签、avoid_if），并自行把冲突改写成卖点。
4. 守卫最初只认强负面词，环境分阈值偏低。单字「吵」、油烟、环境分 6 的店都能漏过。

后来口味（要辣 / 不辣）也出现同类圆场：「虽然清淡，但仍能满足要辣」。所以终版把菜系、辣度一并写进硬需求，并在规则层用 `MILD_PATTERN` / `SPICY_PATTERN` 做对称拦截。

### 3.5 优化方案（Prompt + 规则，必须一起讲）

**Prompt 侧（V3）：**

- 输入里区分 `recommendable` 与 `ineligible`（硬需求冲突，禁止写入 `recommendations`）。`ineligible` 只留店名和冲突原因，不再塞完整分析，减少模型「看完再改口」的材料。
- 「数量不得超过 recommendable 的长度，最多 3 家；不够就少推荐，禁止凑满 3 家」。把配额从「永远 3」改成 `max_recommendations = min(3, recommendable.length)`。
- 硬需求未满足不要圆成推荐；`used_fallback` 为 true 时只推 1 家且必须写 gap。兜底是「库里实在没有更合适的，先给一家并讲清楚差距」，不是「假装找到了三家」。
- 禁止「虽然吵 / 油烟 / 热闹，但仍能满足安静」以及口味上的同类圆场。把失败句式直接写进 Prompt，比只写「要诚实」有效。
- `reason` 不要写与用户需求相反的卖点；用户补了口味必须点名是否满足。

线上 `{merchant_analyses}` 实际长这样（结构示意）：

```
{
  "recommendable": [ { "name": "白玉粤菜", "match_score": ..., "analysis": { ... } } ],
  "ineligible": [ { "name": "西街湘菜馆", "hard_violations": ["评价分析提到吵/油烟/热闹，与安静冲突"] } ],
  "used_fallback": false,
  "max_recommendations": 1
}
```

**规则侧（不写进 Prompt 也要做，否则下一句又圆回来）：**

- `hardNeedViolations`：安静 / 私密时，分析文本匹配吵 / 油烟 / 热闹，或环境分低于 7，则剔除。
- 包间：设施维匹配分过低则剔除。
- 菜系：要粤菜却是湘菜，匹配分过低则剔除。
- 辣 / 不辣：分析文本偏清淡却「要辣」，或偏辣却「不要辣」，则剔除。
- `pickRecommendable`：只把可推荐店交给模型；全军覆没才留匹配最高且有分析的 1 家兜底，并打上 `used_fallback: true`。

这是产品上必须分清的一点：**LLM 擅长写理由，不擅长当闸门。闸门放在规则层。** Prompt 负责禁止圆场句式、限制数量、把 gap 写清楚；规则负责这家店根本不要出现在 `recommendable` 里。

### 3.6 再测（V3）

回归句「周末带父母吃饭，要安静有包间」：

- 只推荐白玉粤菜 1 家，没有凑满 3 家。
- 味正、南苑、西街只出现在 gap。
- 理由不再出现「虽然吵 / 油烟，但能满足安静」。
- `lib/recommend-guard.test.ts` 覆盖：嘈杂剔除、单字「吵」/ 油烟剔除、环境分 6 剔除、包间未命中剔除、要辣遇清淡剔除、ineligible 列表正确。

默认句「带 4 岁小孩，预算 200，想吃粤菜，要有包间」再跑 `test-pipeline.ts`，确认粤菜 + 包间主路径仍出卡，没有被守卫误杀成只剩兜底。

守卫单测和 Prompt 回归要一起看：只测 Prompt，冲突店根本不会进上下文，模型「表现变好」可能只是因为没看见那些店；只测守卫，看不到模型会不会在兜底时仍写圆场句。两条都过，才算这一轮结束。

### 3.7 最终版本

```
你是一个本地生活推荐顾问。基于以下信息：
- 用户需求标签：{user_needs}
- 候选商家评价分析结果：{merchant_analyses}
  （recommendable = 可推荐；ineligible = 硬需求冲突，禁止写入 recommendations）

请生成推荐方案：
1. 只从 recommendable 里按匹配度推荐，数量不得超过 recommendable 的长度，最多 3 家；不够就少推荐，禁止凑满 3 家
2. 每个商家给出"推荐理由"（用自然语言，要具体、有说服力）
3. 每个商家给出"注意事项"（避坑提醒）
4. 硬需求有缺口或 ineligible 非空时，必须在 gap 说明差距

输出必须是且仅是如下 JSON（不要其它字段、不要 markdown）：
{
  "recommendations": [
    { "merchant": string, "reason": string, "notes": string }
  ],
  "gap": string | null
}

规则：
- recommendations 长度必须是 1 到 max_recommendations（即 min(3, recommendable.length)），禁止为凑满 3 家而多写。
- merchant 必须用候选商家的原名。
- reason 必须基于评价数据，不要编造。
- 只从 merchant_analyses.recommendable 里选店；ineligible 里的店禁止出现在 recommendations，原因写进 gap。
- 用户明确提出的硬需求（包间、安静、私密、指定菜系、口味如辣/不辣）未满足时不要圆成推荐。used_fallback 为 true 时只推荐这 1 家，并必须写 gap。
- 用户补了口味时，reason 必须点名是否满足该口味（例如要辣就写辣度相关评价）；对不上就不要推荐，写进 gap。
- 禁止「虽然吵/油烟/热闹，但仍能满足安静」或「虽然清淡，但仍能满足要辣」这类圆场；有冲突就不要推荐，写进 gap。
- reason 里不要写与用户需求相反的卖点。
- notes 写避坑提醒；某维度数据不足时写「该维度数据不足，建议实地体验确认」。
- 存在硬需求缺口或全部不完全匹配时 gap 用字符串说明差距，否则 gap 为 null。
- 用用户的语言风格回应，不要过于正式。
```

**V1 → V2 → V3 对照：**

| 点 | V1 | V2（锁格式） | V3（终版） |
| --- | --- | --- | --- |
| 数量 | 固定 Top 3 | 1–3，schema 可过即可 | `min(3, recommendable.length)`，禁止凑数 |
| 输入 | 候选一股脑 | 同左 | 拆成 recommendable / ineligible / used_fallback |
| 圆场 | 未禁 | 未禁 | 明确禁止「虽然…但仍能满足」 |
| gap | 口头第 4 点 | JSON 字段 | 硬需求缺口或 ineligible 非空时必填 |
| 闸门 | 无 | 无 | `recommend-guard` 先拦截 |

## 4. 三条 Prompt 对照

| 维度 | 需求解析 | 评价分析 | 推荐生成 |
| --- | --- | --- | --- |
| V1 失败类型 | 非 JSON、类型漂、空输入乱补 | 中文键、嵌套、一次输出多家 | 无 schema；默认凑满 3 家 |
| 后一轮失败 | 过度推断（产品用确认页修） | 分数非整数 | 会圆场：虽然吵但仍推荐 |
| 改 Prompt 的抓手 | 锁骨架 + null 规则 | 单店 + 英文扁平键 + 长度 3 | 可推荐集合 + 禁止凑数 + 禁圆场句 |
| 必须用代码兜底 | zod `.strict()`、确认页可改 | 单店失败不填假分；评价不足降权 | `recommend-guard` 硬拦截 |
| 验收命令 | `--only=parse` | `--only=analyze` | `test-pipeline.ts` + guard 单测 |
| 改完仍允许浮动的 | scene 用词（家庭 / 聚餐） | 分数 ±1 | reason 措辞 |
| 改完不允许浮动的 | 键名、null、crowd 类型 | 键名、数组长度、单店对象 | 冲突店不得出现在 recommendations |

三条 Prompt 的迭代顺序也值得单独说：先解析、再分析、最后推荐。推荐的圆场有一部分是前面两步给的脏数据（标签乱编、分析键读不到）造成的。如果一开始就猛改推荐词，会把格式问题和产品问题搅在一起，无法判断是 Prompt 不好还是上下文就是错的。

## 5. 调用层配套（所有 Prompt 共用）

这些不是 Prompt 正文，但没有它们终版会退回 V1：

1. **`chatJSON`：** `response_format: json_object`。DeepSeek 要求 Prompt 里也写明只输出 JSON，否则可能空转或返回非对象。
2. **关闭 thinking：** Demo 要稳定 JSON 和及时 SSE。思考过程会占满约 30 秒超时，结果页看起来像卡住。
3. **`fillPrompt`：** `{key}` 缺参或多余参都抛错，禁止占位符漏进模型。漏一个 `{user_needs}` 进上下文，模型会把它当用户原话理解。
4. **校验失败即失败：** 不截断、不「差不多就展示」。解析失败算该条用例失败。前端展示明确错误，而不是空卡片。
5. **JSON 模式 + Prompt 双重约束：** 只开 API 的 json_object、Prompt 仍写「请给出建议」，模型可能返回 `{ "advice": "..." }`。只写 Prompt 不开 JSON 模式，又容易包 markdown。两边都要。
6. **守卫不写进 Prompt：** 只加「请诚实」，模型仍能看见冲突店的完整分析，配额压力下还是会圆。规则层让它根本看不到那些店。Prompt 里保留禁止圆场句，是为了兜底路径（`used_fallback`）仍可能把冲突店塞回唯一候选时，文案不要再次改口。
