## 1. 背景与问题

到店吃饭前，用户通常已经打开过评价：星级、标签云、按时间排序的长列表都有。真正耗时间的不是「找店」，而是**把模糊约束和互相打架的评价收成一个决定**。

典型困境：

- 需求是口语化的。「带 4 岁小孩，预算 200，想吃粤菜，要有包间」同时包含场景、预算、菜系、设施，搜索筛选项对不齐。
- 评价是非结构化的。安静、等位、对小孩是否友好散落在几十条口语句里，用户自己做摘要。
- 平台推荐偏热度与距离，**不会解释「为什么适合你这顿」**，更不会主动标出「这家不适合你」的坑。
- 通用聊天模型可以点名餐厅，但容易编造菜单、设施和口碑，无法核对出处。

探店参谋卡在「已经决定出门吃饭 → 还没下单」这一段：先理解需求，再只对库存评价做分析，最后给出可解释、可拒绝的推荐。

## 2. 目标与非目标

### 2.1 产品目标

1. 用户用一句话完成需求表达，并在进推荐前能看见、改掉系统的理解。
2. 推荐最多 3 家，每家必须带理由、评价原文摘录、避坑；五维分析标明来自评价语义。
3. 用户明确提出的硬需求（包间、安静/私密、指定菜系、辣/不辣）未被满足时，该店不得靠文案进入推荐列表。
4. 用户能在本轮内追问、看商户视角、确认「去了哪家」；失败态可恢复，不出现空白页。

### 2.2 本阶段业务目标

- 验证「需求驱动 + 评价可溯源」是否比「再看一遍评价列表」更适合演示与决策。
- 用种子评价库跑通解析 → 匹配 → 分析 → 推荐 → 选择的闭环，便于后续替换真实评价源。

### 2.3 非目标（V1 明确不做）

| 不做 | 原因 |
| --- | --- |
| 接入美团 / 大众点评开放接口 | Demo 阶段无法稳定拿到生产数据；先锁产品逻辑 |
| 下单、预订、排队、支付 | 履约不在决策助手范围内 |
| 实时营业、库存、路况 | 无数据源，禁止模型编造 |
| 地图选点、多城市切换 | 当前库为上海模拟商圈 |
| 账号体系、社交分享 | 增加复杂度，无助于验证主路径 |
| 独立商户后台 | 商户视角是同一结果卡上的读法切换 |
| 语音输入 | 非主路径，不纳入本版验收 |

## 3. 产品定位

**一句话定位：** 探店参谋是到店餐饮的 AI 决策助手——你说出这顿饭怎么吃，它从评价里找出该去哪家，并讲清楚依据和坑。

**角色定义：** 大模型是分析师，不是聊天机器人。它不得在库存之外点名餐厅，不得编造评价里没有的菜品、价格、设施。

**与替代方案的差异：**

| 方案 | 用户得到什么 | 探店参谋的差别 |
| --- | --- | --- |
| 评价列表 + 人工筛选 | 信息堆砌，总结在人身上 | 先对齐需求，再抽取与排序 |
| 通用聊天「推荐几家店」 | 店名和理由，难核对 | 先匹配库内店，理由绑定评价原文 |
| 仅按评分/热度排序 | 热门店，不一定适合今晚 | 硬需求拦截 + 可解释匹配分 |

价值主张对应三条用户收益：

1. 少翻评价：系统把口碑收成五维、标签和避坑。
2. 模糊需求可执行：口语进、标签出，用户可改。
3. 降低踩坑：差评信号单独呈现，不完全匹配会写差距。

## 4. 用户与使用场景

### 4.1 主用户：到店决策者

- **画像：** 20–35 岁城市消费者，为约会、家庭聚餐、同事聚餐或独食做决定。
- **习惯：** 会看评价，但不愿把 20–30 条差评和好评自己归纳。
- **约束：** 时间紧、条件多（预算、菜系、包间、带小孩、不要太辣），条件之间可能冲突。
- **成功标准：** 3 分钟内得到 1–3 家「能讲清为什么」的选项，并愿意点出今晚去哪家。

### 4.2 次用户：看经营信号的店主（演示向）

- **画像：** 餐饮店经营者或运营，关心「顾客在评价里到底在意什么」。
- **入口：** 不单独注册，在已推荐的店铺卡片上切换「商户视角」。
- **成功标准：** 同一份评价能读出在意点、差评焦点、优势与警惕项，而不是另一套生成话术。

### 4.3 核心场景

| ID | 场景 | 输入示例 | 期望 |
| --- | --- | --- | --- |
| S1 | 家庭聚餐 | 带 4 岁小孩，预算 200，想吃粤菜，要有包间 | 拆出家庭/预算/粤菜/包间；无包间店不进推荐 |
| S2 | 约会 | 周末约会，要安静，人均 150 到 200 | 氛围含安静；过吵的店拦截或进差距 |
| S3 | 同事聚餐 | 同事聚餐，人均 100 左右，不要太辣 | 口味约束必须在理由或淘汰中体现 |
| S4 | 条件放宽 | 一个人随便吃，家常菜就行 | 允许更宽匹配，仍要有避坑 |
| S5 | 追问 | 第一家有没有适合小孩的菜？ | 只根据已有评价答；没有就明说 |
| S6 | 改标签再搜 | 确认页把菜系改成火锅 | 后续分析使用改后的条件 |

### 4.4 用户故事

1. 作为决策者，我想用一句话说清今晚怎么吃，以便不用先填一堆筛选项。
2. 作为决策者，我想在出结果前看到系统理解成了哪些条件，以便改掉误解析。
3. 作为决策者，我想看到最多三家店以及「为什么是这家」，以便向同行的人解释。
4. 作为决策者，我想先看到坑（等位、太吵、不适合小孩），以便做去风险选择。
5. 作为决策者，我想追问某一家的细节，以便不用离开当前推荐重搜。
6. 作为决策者，我想告诉系统我去了哪家，以便后续选择率更接近真实行为。
7. 作为店主（演示），我想从同一份评价看到经营侧摘要，以便理解 C/B 共用数据层。

## 5. 信息架构与页面

| 路由 | 页面 | 职责 |
| --- | --- | --- |
| `/` | 首页 | 表达需求、场景模板、热门店镜头、产品三步说明 |
| `/confirm?query=` | 确认页 | 展示原句、解析标签、推断说明、允许改标签 |
| `/results` | 结果页 | 分析进度、推荐卡片、追问、商户视角、选择 |
| `/thanks?shop=` | 感谢页 | 确认已记录去向，数秒后回首页 |

客户端在确认后把需求写入会话存储，结果页读取；无需求则回首页。推荐成功后创建推荐场次，用于曝光与「每轮只选一家」。

## 6. 功能需求

下列每条均含**规则**与**验收**。未写优先级的均为 P0（主路径必须）。

### 6.1 F1 需求理解（P0）

**描述：** 将用户自然语言解析为结构化条件，并允许修正。

**输入：**

- 首页输入框，最长 500 字。
- 场景模板：周末约会、同事聚餐、家庭聚餐、一个人随便吃；同一模板多次点击轮换不同例句。

**输出字段（与解析模型锁定）：**

| 字段 | 含义 | 空值规则 |
| --- | --- | --- |
| scene | 场景 | 未提及则为空 |
| budget | 人均预算，字符串如 `200`、`150-200` | 未提及为空 |
| cuisine | 菜系 | 未提及为空 |
| taste | 口味约束 | 未提及为空 |
| atmosphere | 氛围 | 未提及为空 |
| facility | 设施 | 未提及为空 |
| crowd | 人数，整数 | 未提及为空 |
| time | 时间 | 未提及为空 |
| location | 位置/商圈 | 未提及为空 |
| inference | 推断说明，必填非空 | 无法解析时写明原因 |

**规则：**

- 用户未提及的字段不得编造成具体值。
- 空输入或无意义输入（如单字「吃」）：除 `inference` 外全部为空。
- 确认页展示「你刚才说」原句；标签可点开修改；人数必须是数字；预算展示可带「人均」前缀，回写时去掉前缀。
- 清空某标签视为该条件不参与后续匹配。

**验收：**

- 固定句「带 4 岁小孩，预算 200，想吃粤菜，要有包间」应拆出预算、粤菜、包间，场景偏向家庭/带小孩；`inference` 非空。
- 解析失败：展示错误态，提供「再试一次」和「回首页」，无空白页。
- 无 query 进入确认页：提示回首页。

### 6.2 F2 评价语义分析（P0）

**描述：** 对进入分析的每家候选店，基于其评价生成五维分数与洞察。

**五维（每维 1–10 整数）：** 出品（taste_quality）、环境、服务、性价比、场景适配。

**同时产出：** 3 个正面标签、3 个风险信号、最适场景、不推荐情形。

**展示：**

- 结果卡使用雷达图，轴标签为出品 / 环境 / 服务 / 性价比 / 场景，旁注分数。
- 文案：「五维来自评价语义，不是官方星级」。
- 标题旁提供「AI 分析说明」：拆需求、算匹配、读评价写结论。

**规则：**

- 评价条数 &lt; 5：`dataInsufficient = true`，卡片提示「评价数据不足，推荐结果仅供参考」，先验选择率再打折。
- 单店分析失败：该店 `analysis` 可空并带错误信息，不得用假分数填满雷达充数。
- 雷达无有效分数时只显示网格，不画伪造多边形。

**验收：**

- 有分析的店：五维均为 1–10，雷达可见。
- 不足 5 条评价的店若仍出现，必须带数据不足提示。

### 6.3 F3 匹配、拦截与推荐生成（P0）

**描述：** 先用规则从库中取出候选并打分，再过滤硬需求冲突，最后由模型生成最多 3 条推荐文案。

**匹配权重（用户未提的维度不参与加权）：**

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 菜系 | 0.28 | 硬需求，对不上接近 0 分 |
| 预算 | 0.22 | 解析区间与人均价比较 |
| 位置 | 0.13 | 商圈/地址弱包含 |
| 设施 | 0.12 | 如包间 |
| 口味 | 0.12 | 如辣 / 不辣 |
| 氛围 | 0.08 | 如安静 |
| 场景 | 0.05 | 软匹配 |
| 选择率 | 0.06 | 弱加权，不得压过菜系/包间/辣 |

候选上限 5 家进入分析；推荐卡片最多 3 家。

**硬需求拦截（不得「虽然吵但仍适合安静」）：**

- 用户要安静/私密：评价或分析文本出现过吵、热闹、油烟等，或环境分过低，则不可推荐。
- 用户要包间而标签/分析对不上：不可推荐。
- 用户指定菜系或辣/不辣而对不上：不可推荐，理由里禁止反向卖点。
- 被拦截的店只允许出现在差距说明（gap）中，禁止写入 `recommendations`。

**推荐模型输出：**

- `recommendations[]`：`merchant`（必须用库内原名）、`reason`、`notes`。
- `gap`：有硬需求缺口或无一完全匹配时必须为说明字符串，否则为 null。
- 可推荐集合为空或仅 1 家时，不得为凑满 3 家而编店。

**验收：**

- 卡片店名能对上分析候选。
- 展示匹配分与选择率（选择率为平滑后的 0–1，卡片用百分展示）。
- 理由下方至少尽量给出评价原文摘录（最多 2–3 条）；没有则明示暂无原文。
- 存在 gap 时结果页单独展示「差距说明」。

### 6.4 F4 避坑提醒（P0）

**描述：** 每张推荐卡必须有注意事项，对应风险而非重复卖点。

**规则：**

- `notes` 非空。
- 某维数据不足时，应出现「该维度数据不足，建议实地体验确认」或同等含义。
- 视觉：浅黄底区块，标题「避坑提醒」，与白色卡片、品牌黄主按钮区分。

**验收：** 三家卡均可见避坑文案；不得整段复制推荐理由。

### 6.5 F5 多轮追问（P0）

**描述：** 用户在已有推荐上下文中继续提问。

**规则：**

- 上下文 = 本轮需求标签 + 已生成推荐 + 候选评价分析 + 最近对话（有上限）。
- 只根据上述信息回答；禁止编菜单、价格、未记载的设施。
- 评价未提及则明确说「评价里没提到，建议到店确认」。
- 口语短段落，不输出 JSON。
- 输入为空不可发送；失败保留原文并提供重试，不丢用户那一句。

**验收：**

- 占位示例「第一家有没有适合小孩的菜？」可发出并流式显示回复。
- 问库存外事实时，回复不得捏造具体菜名（除非评价原文出现）。

### 6.6 F6 商户视角（P1，主路径演示建议包含）

**描述：** 在某张已推荐卡片上切换读法，不离开结果页。

**内容：** 顾客最在意、差评集中在、差异化优势、需要警惕；五维用与顾客侧同一套雷达（紧凑样式）。

**规则：**

- 首次展开再请求洞察；失败可重试；空数据给空态。
- 洞察必须基于该店评价，不得换成另一家店的结论。
- 按钮文案：关闭前为「切换商户视角」，打开后为「回到顾客视角」。

**验收：** 展开后四段文案 + 雷达；关闭后卡片回到顾客信息架构。

### 6.7 F7 确认去向与选择率（P0）

**描述：** 用户声明本轮实际去哪家，系统记一次选择。

**规则：**

- 推荐露出的店记曝光；同一 `sessionId` 只能有一条选择。
- 来源：`card`（卡片按钮「我就去这家」）或 `search`（底部搜店名后确认）。
- 已选择后，卡片按钮与搜店确认禁用；展示已选店名。
- 选择成功进入感谢页，展示店名，说明选择率会更新，约 4 秒回首页，可立即回首页。
- 场次未创建时，不得假装已记录，需提示刷新结果页。

**选择率：**

- 先验 `priorRate` 由评价均分、好评占比、负面标签（等位久、分量少、服务差、太吵、性价比低、停车难等）计算。
- 展示值 = 先验与实际曝光/选择的 Beta 平滑，避免 0 曝光时剧烈跳动。
- 首页「热门」可按选择率、餐段、先验等镜头轮换；加载失败用错误态，库空用空态。

**验收：**

- 第一次点「我就去这家」成功跳转感谢页。
- 同一轮再次选择被拒绝或按钮不可用。
- 搜到的店若不在本轮推荐中，仍允许作为 search 来源记下（实现以接口为准：须为库内合法 `merchantId`）。

### 6.8 F8 空态、错态与等待（P0）

| 情况 | 表现 |
| --- | --- |
| 全局未捕获错误 | 错误页，可重试 |
| 首页热门失败/空库 | 明确文案，仍允许输入需求 |
| 无候选 / 模型 0 张卡 | 空态，引导换句或回首页 |
| 分析中 | 骨架 + 进度文案轮播（匹配商家、分析评价、提取口味、生成理由） |
| 接口超时 / 模型 JSON 非法 | 可读中文错误，可重试 |

**验收：** 上述路径均无白屏、无静默失败。

## 7. 用户流程

### 7.1 主路径

```
打开首页
  → 输入或点场景模板
  → 确认页：核对/改标签
  → 点「按这个找店」
  → 结果页：分析进度
  → 阅读 Top 3、雷达、避坑
  → （可选）追问
  → （可选）商户视角
  → 「我就去这家」或搜店确认
  → 感谢页
  → 回首页
```

### 7.2 分支

- **改条件：** 仅在确认页改标签；结果页不提供「返回改标签」也可通过回首页重来（若后续加「回确认页」视为增强，非 V1 必验）。
- **无推荐：** 停在结果空态，可回首页。
- **只浏览不选择：** 允许离开；本轮无 UserChoice。
- **追问多轮：** 允许，次数受接口上限约束。

### 7.3 异常流

```
解析失败 → 再试 / 回首页
结果页无缓存需求 → 回首页
分析或推荐失败 → 再试
追问失败 → 保留问句，再试
记选择失败 → 页内错误，不跳感谢页
```

### 7.4 流程规则

- 未确认需求不得进入有效推荐（无 session 存储则重定向）。
- 未生成推荐不得创建「已选」记录。
- 等待超过用户预期时，进度文案必须变化，避免误以为死机。

## 8. 数据需求

### 8.1 领域对象

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| 商家 | 名称、菜系、人均、地址、商圈、先验选择率、曝光、选择次数 | 匹配与展示 |
| 评价 | 评分 1–5、正文、时间、情感 | 语义分析与原文引用 |
| 标签 | 挂在评价下的短语 | 硬需求与先验 |
| 推荐场次 | 需求 JSON、创建时间 | 一轮决策 |
| 曝光 | 场次 + 商家 + 名次 | 选择率分母 |
| 用户选择 | 场次唯一、商家、来源 card/search | 选择率分子 |

### 8.2 种子数据约定（V1）

- 规模：50 家店，每家约 20–30 条评价。
- 地理：上海模拟商圈与街道，店名为虚构组合，**不得对用户宣称是真实门店**。
- 文风：口语、少量错别字，情感大约正:中:负 ≈ 6:3:1，用于验证抽取而非刷好评。
- 替换真实数据时：保持商家–评价–标签结构，重跑先验选择率；产品流程不变。

### 8.3 运行时数据

- 本地：SQLite。
- 线上：可写库（Turso）。无写库时不得出现「只读库」导致主路径在记场次处失败且无说明。

## 9. AI 行为规范

### 9.1 调用边界

仅在这些动作请求模型：需求解析、候选评价分析、推荐生成、追问、商户洞察。打开首页、只读静态内容不消耗模型额度。

### 9.2 输出约束

- 解析、分析、推荐必须是可校验 JSON，字段名锁定；校验失败整单失败，禁止截断凑合展示。
- 推荐 `merchant` 必须是候选原名。
- 追问禁止 JSON/标题体，禁止编造。

### 9.3 幻觉与主观性

- 结论是「基于评价的 AI 分析」，不是平台官方星级或卫生评级。
- 无出处的设施、菜品、价格不得当作事实。
- 用户已表达的硬需求与评价冲突时，淘汰或写 gap，禁止圆场句式。

### 9.4 降级

- 单店分析失败：跳过该店分析，不影响其他店。
- 全部失败或 0 候选：空/错态，引导改条件。
- 密钥缺失：明确配置错误，不发起空鉴权请求。

## 10. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 端 | 以手机优先；输入字号避免 iOS 缩放；底栏为安全区留白 |
| 性能 | 解析一次模型调用；分析对候选店串行/并行以实现为准，结果页必须有进度反馈 |
| 可用 | 主路径含模型等待，一次完整走通约 3 分钟 |
| 安全 | 密钥只放环境变量；`.env*` 不入库 |
| 公开访问 | 线上链接无需登录；须知他人走推荐会消耗项目方模型额度 |
| 网络 | `vercel.app` 在部分网络不可达，文档中说明可用流量打开 |
| 兼容 | 现代移动浏览器；不承诺 IE |
| 文案 | 中文产品界面；错误信息对用户可读 |

## 11. 指标与验收

### 11.1 主路径验收（必须）

1. S1 固定句从首页走到至少 1 张推荐卡。
2. 卡上同时具备：理由、避坑、雷达或数据不足说明、尽量有原文。
3. 硬需求句下，明显冲突店不出现在推荐列表。
4. 追问一句有回复。
5. 「我就去这家」到达感谢页。
6. 人为断网或错误密钥时，出现错误态而非白屏。

### 11.2 上线后建议观测（有真实流量再看）

| 指标 | 定义 | 观察方式 |
| --- | --- | --- |
| 解析可用率 | 确认页成功展示标签的会话 / 发起解析 | 前端或 parse 成功率 |
| 推荐完成率 | 产生 ≥1 张卡 / 进入结果页 | 结果页 ready |
| 可溯源率 | 带原文摘录的卡片 / 全部卡片 | 抽检 |
| 硬需求误推率 | 抽检中「应拦截却推荐」的比例 | 人工+用例 |
| 选择率 | 记选择的场次 / 有曝光的场次 | UserChoice / Session |
| 追问使用率 | 发过追问的结果页 / 全部结果页 | 追问 API |

V1 不设平台级数值 KPI；种子库上的百分比仅作回归用例，不作增长承诺。

## 12. 风险与约束

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 模型偶发非 JSON / 超时 | 主路径失败 | 校验失败即错态；超时提示重试；进度缓解等待 |
| 种子数据被当成真店 | 信任与合规 | 文档声明模拟；店名可识别为虚构组合 |
| 公开链接被刷推荐 | 额度消耗 | 可暂停托管或轮换密钥；不在仓库写密钥 |
| 线上库只读 | 无法记场次与选择 | 生产必须可写库 |
| 国内访问托管域名失败 | 演示中断 | 备用流量 / 本机演示 |
| 选择率冷启动 | 首页热门空洞 | 先验 + 不足时回退全库 |
