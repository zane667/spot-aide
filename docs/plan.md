## 01 选题推荐：三个方向

以下三个方向均紧扣美团AI战略（小团/CatPaw/LongCat），技术难度适合1-2周独立完成，且能体现「理解AI能力边界 + 产品思维 + 从0到1」的核心能力。

### 方案一：探店参谋 —— AI评价洞察与智能决策助手（强烈推荐）

**为什么推荐这个方案：** 直接对标美团「小团」（C端AI决策助手）和「CatPaw」（B端商家AI经营助手）双产品线。展示候选人对美团本地生活业务的深度理解，同时覆盖C端用户决策和B端经营分析两个视角。

## 02 最终方案详细设计：探店参谋

一个基于AI评价挖掘的智能探店决策助手——让模糊的需求变成清晰的行动建议。

### 产品定位与目标用户

**一句话定位：** 基于真实用户评价的AI探店决策助手——你只需说出需求，AI帮你从海量评价中找到最佳答案。

#### 目标用户

- **主要用户：** 20-35岁城市消费者，有到店聚餐/约会/团建需求，决策时依赖评价但被信息淹没
- **次要用户（Demo展示用）：** 模拟的餐饮商户，可以看到AI如何从评价中提取经营建议

#### 核心价值主张

- 用户不再需要翻阅几百条评价自己总结 → AI直接从评价中提炼结构化洞察
- 模糊需求（「适合约会的安静餐厅」）→ AI理解语义并精准匹配
- 评价中的「坑」被显式标注 → AI自动识别差评中的风险信号

### 核心功能清单（MVP范围）

#### F1 智能需求理解

用户用自然语言描述需求（如「周末带父母吃饭，要安静、有包间、不要太辣」），AI解析出结构化标签：场景=家庭聚餐、氛围=安静、设施=包间、口味=不辣。

#### F2 评价语义分析引擎

对商家评价进行多维度语义分析——口味、环境、服务、性价比、适合场景等，生成雷达图和关键洞察摘要，而不是简单的评分。

#### F3 智能推荐排序

基于用户需求标签与评价洞察的匹配度进行排序，并解释「为什么推荐这家」——不是黑盒推荐，而是让用户理解推荐逻辑。

#### F4 避坑提醒

AI自动从差评中提取高频风险信号（如「等位时间长」「菜品分量少」「服务态度差」），以「避坑提醒」形式呈现，帮助用户做出去风险决策。

#### F5 商户经营洞察（加分功能）

切换「商户视角」，AI从评价中提取经营优化建议——顾客最在意什么、差评集中在哪、与竞品的差异化优势是什么。直接对标CatPaw。

### AI能力使用方案

#### 模型选择：DeepSeek API（推荐）或 OpenAI GPT-4o-mini

| 维度 | DeepSeek-V3 | GPT-4o-mini | 选择理由 |
| --- | --- | --- | --- |
| 中文理解 | 极强 | 强 | 中文评价场景，DeepSeek中文理解更强 |
| 价格 | 极低成本 | 低成本 | Demo阶段成本可控，DeepSeek更便宜 |
| Function Call | 支持 | 支持 | 都需要结构化输出能力 |
| 面试加分 | 国产模型，贴合美团 | 通用性强 | 美团自研LongCat，用国产模型更有话题 |

**面试话术建议：** 「我选择DeepSeek API是因为：第一，中文评价理解效果更好；第二，成本低适合个人项目；第三，美团的LongCat也是国产自研大模型，我在选择模型时的思考逻辑与美团的AI战略方向是一致的。如果正式落地，我会优先评估LongCat的能力表现。」

#### 核心Prompt设计

**Prompt 1：需求解析（用户输入 → 结构化标签）**

```
System Prompt

你是一个本地生活消费场景的需求解析助手。你的任务是将用户用自然语言描述的到店消费需求，解析为结构化的标签。

解析维度：
- scene: 场景（聚餐/约会/商务/家庭/独食/团建）
- budget: 人均预算（数字范围，单位：元）
- cuisine: 菜系偏好（中餐/日料/西餐/火锅/烧烤...）
- taste: 口味约束（不辣/偏甜/清淡...）
- atmosphere: 氛围要求（安静/热闹/浪漫/私密...）
- facility: 设施要求（包间/停车/WiFi/无障碍...）
- crowd: 人数（数字）
- time: 时间约束（工作日/周末/午餐/晚餐）
- location: 位置偏好（商圈/地铁站附近）

输出JSON格式，每个字段如果用户未提及则填null。
对模糊表述做合理推断，但必须在"inference"字段说明推断依据。
```

**Prompt 2：评价语义分析（多条评价 → 多维度洞察）**

```
System Prompt

你是一个餐饮评价分析专家。请对以下用户评价进行多维度语义分析。

分析维度（每个维度1-10分）：
1. 口味质量（食材新鲜度、味道层次、出品稳定性）
2. 环境体验（装修、噪音、座位舒适度、卫生）
3. 服务质量（响应速度、态度、专业度）
4. 性价比（价格与品质的匹配度、分量）
5. 场景适配度（适合哪些消费场景）

同时提取：
- top_tags: 最突出的3个正面标签
- risk_signals: 最突出的3个负面风险信号
- best_for: 最适合的消费场景
- avoid_if: 什么情况下不推荐

输出严格的JSON格式。
```

**Prompt 3：推荐生成（匹配 + 解释）**

```
System Prompt

你是一个本地生活推荐顾问。基于以下信息：
- 用户需求标签：{user_needs}
- 候选商家评价分析结果：{merchant_analyses}

请生成推荐方案：
1. 按匹配度排序，推荐Top 3商家
2. 每个商家给出"推荐理由"（用自然语言，要具体、有说服力）
3. 每个商家给出"注意事项"（避坑提醒）
4. 如果所有商家都不完全满足需求，说明差距在哪里

注意：
- 推荐理由必须基于评价数据，不要编造
- 如果某个维度数据不足，明确标注"该维度数据不足，建议实地体验确认"
- 用用户的语言风格回应，不要过于正式
```

#### AI能力边界处理（面试重点考察）

- **幻觉防护：** 所有推荐结论必须标注数据来源（引用具体评价片段），不允许AI凭空生成推荐语。Prompt中明确要求「基于评价数据，不要编造」。
- **数据不足处理：** 当某个商家评价数量少于5条时，明确标注「评价数据不足，推荐结果仅供参考」，并在UI上降低该商家的排序权重。
- **主观性标注：** AI给出的评分和标签标注为「AI分析结果，基于用户评价语义提取」，而非平台官方评分。避免用户误以为是权威结论。
- **错误兜底：** 当AI无法解析需求或匹配结果为空时，不返回空页面，而是给出引导性提示（如「试试放宽预算范围？」或「附近可能没有完全匹配的，要不要看看类似风格的？」）。
- **时效性限制：** 标注评价数据的分析时间范围，明确告知用户「评价分析基于近6个月数据」，避免过期信息误导。

### 技术架构

| 角色 | 选型 | 理由 |
| --- | --- | --- |
| 前端框架 | Next.js 14 + Tailwind CSS | Cursor对Next.js支持最好，彭子言已有经验；Tailwind快速出UI；App Router支持流式渲染AI响应 |
| AI接入 | DeepSeek API / OpenAI SDK | API调用简单，支持Function Call和流式输出；用Vercel AI SDK封装流式渲染 |
| 数据存储 | SQLite + Prisma | Demo阶段轻量够用，预置50-100家模拟商家数据；无需额外部署数据库服务 |
| 部署方案 | Vercel 免费部署 | Next.js原生支持，一键部署；面试官直接打开链接体验；免费额度足够Demo |
| 图表可视化 | Recharts | React原生图表库，用于评价分析雷达图；轻量、美观 |
| 辅助工具 | Cursor / v0.dev | Cursor负责全栈开发；v0.dev可快速生成UI组件原型 |

#### 系统架构（简化）

用户输入（自然语言需求） → Next.js API Route（需求解析Prompt） → DeepSeek API（结构化标签提取） → SQLite查询（匹配候选商家） → 评价分析Prompt（多维度语义分析） → 推荐生成（排序 + 解释 + 避坑）

**关于模拟数据的说明：** Demo不需要真实接入美团API。提前准备50-100家模拟商家数据（名称、菜系、均价、地址、20-50条模拟评价）。评价数据要有真实感——包含正面、中性、负面，包含口语化表达、错别字等。这本身就是产品设计的一部分（数据设计能力）。

### 用户体验流程

#### 完整用户旅程

打开首页（一句话引导） → 输入需求（自然语言 / 快捷模板） → AI解析确认（展示理解 + 可修正） → 加载分析（流式输出进度） → 结果展示（推荐 + 雷达图 + 避坑） → 追问 / 调整（多轮对话）

#### 详细步骤说明

1. **首页：** 顶部一个大输入框，下方有3-4个场景快捷模板（「周末约会」「同事聚餐」「家庭聚餐」「一个人随便吃」）。简洁、聚焦，降低用户思考成本。
2. **输入需求：** 用户可以自由输入，也可以点模板快速体验。支持语音输入（加分项，调用浏览器原生Speech API）。
3. **AI解析确认：** AI将用户需求解析为标签后，以Tag形式展示（如 家庭聚餐 | 人均150-200 | 粤菜 | 安静 | 有停车），用户可以点击修改任何标签。
4. **分析过程：** 流式输出分析进度——「正在分析32条评价...」「正在提取口味维度...」「正在匹配最佳商家...」——让用户感知AI在做什么，减少等待焦虑。
5. **结果展示：** Top 3推荐卡片，每张卡片包含：商家名称、匹配度百分比、推荐理由（引用具体评价原文）、评价雷达图（5维）、避坑提醒。
6. **追问交互：** 用户可以继续追问（如「第一家有没有适合小孩吃的菜？」），AI基于上下文给出回答。展示多轮对话能力。

### 产品评估指标

如何衡量这个AI产品「好不好」——展示产品经理的数据思维：

| 指标类别 | 具体指标 | 衡量方式 | 目标值 |
| --- | --- | --- | --- |
| AI理解准确率 | 需求解析正确率 | 标注100条测试用例，对比AI解析结果与人工标注 | ≥ 85% |
| 推荐有效性 | 用户采纳率 | 用户查看推荐后是否点击「详情」或继续追问 | ≥ 60% |
| 幻觉控制 | 推荐信息可溯源率 | AI生成的推荐语中，有多少可以追溯到具体评价 | ≥ 90% |
| 用户满意度 | 任务完成率 | 用户是否最终获得了一个明确的推荐结果 | ≥ 80% |
| 效率提升 | 决策耗时对比 | 使用产品前后的「从打开到做决定」时间对比 | 减少50%+时间 |
| 体验质量 | 等待感知时长 | 通过流式进度展示，用户主观等待感受 | 用户评价「可接受」 |

## 03 开发排期：14天详细计划

按天拆解，每天2-4小时投入，确保可执行。

### Phase 1：数据准备与Prompt调试（Day 1 - Day 3）

- **Day 1：** 搭建Next.js项目骨架（用create-next-app + Tailwind）；注册DeepSeek API，跑通基础API调用；用Cursor生成项目目录结构。
- **Day 2：** 设计模拟数据Schema（商家表、评价表、标签表）；用AI批量生成50家模拟商家数据（含名称、菜系、均价、地址）；为每家商家生成20-30条模拟评价。
- **Day 3：** 反复调试3个核心Prompt（需求解析、评价分析、推荐生成）；用Cursor辅助生成测试用例；确保输出格式稳定为JSON，处理各种边界情况。

### Phase 2：核心后端逻辑（Day 4 - Day 6）

- **Day 4：** 实现需求解析API Route——接收用户输入，调用DeepSeek，返回结构化标签；处理API错误、超时、格式异常。
- **Day 5：** 实现评价分析API Route——根据解析出的标签查询匹配商家，对每个商家的评价进行批量语义分析；实现SQLite查询逻辑和标签匹配算法。
- **Day 6：** 实现推荐生成API Route——汇总分析结果，生成最终推荐；实现流式输出（SSE）；打通完整后端链路。

### Phase 3：前端页面开发（Day 7 - Day 10）

- **Day 7：** 首页开发——大输入框、快捷模板、简洁Hero区域；参考小团的交互设计；用v0.dev或Cursor快速生成UI。
- **Day 8：** 需求确认页——展示AI解析出的标签（可编辑Tag形式）；加载动画和流式进度条；结果页框架搭建。
- **Day 9：** 结果展示页——推荐卡片组件（商家名、匹配度、推荐理由）；集成Recharts雷达图；避坑提醒组件；流式渲染AI回复。
- **Day 10：** 多轮对话组件——追问功能实现；上下文保持；「切换商户视角」功能（加分项，展示CatPaw对标）。

### Phase 4：联调与体验优化（Day 11 - Day 12）

- **Day 11：** 全链路联调——从输入到结果的完整流程走通；修复API调用bug、数据格式问题；优化加载速度和错误处理。
- **Day 12：** 体验打磨——添加Loading骨架屏；优化移动端适配；添加空状态和错误状态设计；添加「AI分析说明」tooltip（解释AI是怎么得出结论的）。

### Phase 5：部署与面试准备（Day 13 - Day 14）

- **Day 13：** 部署到Vercel——配置环境变量、域名；录制Demo演示视频（3-5分钟）；编写README文档（项目介绍、技术架构、产品设计思路）。
- **Day 14：** 准备面试话术——产品思考（为什么做这个）、技术选型（为什么选这些工具）、AI能力边界处理（怎么处理幻觉）、与美团业务的关联。反复演练Demo演示流程。

### 关键里程碑检查点

- **Day 3结束：** API能跑通，Prompt输出稳定 → 如果没达到，Day 4-5继续调
- **Day 6结束：** 后端链路完整，命令行能看到完整推荐结果 → 这是最关键的技术里程碑
- **Day 10结束：** 前端可用，全流程可走通 → 后面4天纯优化
- **Day 12结束：** 体验打磨完毕，自己满意 → 如果时间不够，Day 12必须冻结功能

## 04 面试展示要点

怎么在面试中讲这个项目，让面试官认可你的AI产品能力。

### Demo演示流程（3分钟）

- 打开产品首页 → 「这是一个AI探店决策助手」
- 输入需求 → 展示AI实时解析为结构化标签
- 查看推荐结果 → 展示雷达图、推荐理由引用评价原文
- 点击「避坑提醒」 → 展示差评风险信号提取
- 追问「有没有适合小孩的？」 → 展示多轮对话
- 切换「商户视角」 → 展示经营洞察（CatPaw对标）

### 产品设计思考（必讲）

- **为什么做这个：** 「观察到用户在美团选餐厅时，需要翻阅大量评价做决策，信息过载是核心痛点。美团的『小团』正在解决这类问题，我想做一个垂直在评价分析场景的Demo。」
- **为什么不是ChatGPT套壳：** 「核心差异在于数据层——我不是让LLM凭空推荐，而是基于真实评价数据进行语义分析，输出有据可依。LLM在这里的角色是『分析师』而非『聊天机器人』。」
- **对AI能力边界的理解：** 「LLM擅长语义理解和信息提取，但不擅长事实判断。所以我在产品设计上做了几个关键决策：①所有推荐必须引用评价原文（防幻觉）②数据不足时明确告知用户 ③AI结论标注为『参考』而非『权威』。」

### 与美团业务的关联（加分）

- **对标小团：** 「小团的核心是『从帮用户找答案到帮用户把事办成』，我的产品在『找答案』环节做了垂直深入——用AI评价分析帮用户更快做决策。」
- **对标CatPaw：** 「商户视角功能展示了AI如何帮商户理解顾客真实需求。CatPaw在做类似的事——帮商家从评价中提炼经营洞察。」
- **对LongCat的思考：** 「如果接入LongCat，我会利用它的代码和Agent能力，让产品不仅推荐，还能直接帮用户完成下单（Agent执行能力）。」
- **对美团AI战略的理解：** 「美团的AI布局是『用户侧 + 商户侧 + 履约侧』三层。我的产品同时涉及用户决策和商户洞察，与美团的双端AI战略方向一致。」

### 防御性问题准备

- **「数据是假的，有什么说服力？」** → 「Demo阶段用模拟数据验证产品逻辑和交互体验。正式上线需要接入真实评价数据，核心挑战是数据质量和实时性。」
- **「和大众点评的AI功能有什么区别？」** → 「大众点评是『评价列表 + 排序』，用户仍需要自己判断。我的产品是『AI先理解你的需求，再从评价中提取匹配的洞察』——是需求驱动的决策，不是信息堆砌。」
- **「如果LLM给出错误推荐怎么办？」** → 「三层防护：①所有结论必须引用原文 ②低置信度结果标注『仅供参考』 ③用户反馈机制持续优化Prompt。」
- **「为什么不用美团的技术栈？」** → 「我选择自己最熟悉的Next.js + Cursor快速交付MVP。作为产品经理，核心能力是『用合适的工具解决问题』，而不是『用最先进的技术』。如果加入美团，我会快速学习内部技术栈。」

### 这个Demo展示的核心能力矩阵

- **理解AI能力边界：** Prompt设计、幻觉处理、数据不足时的降级策略
- **产品思维：** 用户痛点分析、需求拆解、交互设计、评估指标
- **从0到1能力：** 独立完成产品设计 → 技术开发 → 部署上线全流程
- **业务sense：** 对美团AI战略（小团 / CatPaw / LongCat）的深度理解
- **技术执行力：** Cursor + vibe coding快速交付MVP的能力
- **AI工具使用经验：** 用Cursor开发、用AI设计Prompt、用AI生成数据

### 面试前必做的准备清单

1. **产品文档（PRD）：** 写一份简版PRD（1-2页），包含产品定位、目标用户、核心功能、用户流程。面试时主动展示「我是先做产品思考，再做技术实现的」。
2. **原型图：** 用Figma做一个3-5页的高保真原型（首页、需求确认页、结果页）。即使产品已经开发完成，原型图也能展示「产品先行」的思维。
3. **数据设计文档：** 说明为什么这样设计模拟数据，评价数据的分布策略（正面/中性/负面比例、口语化程度等）。
4. **Prompt设计文档：** 把三个核心Prompt的迭代过程记录下来——初始版本 → 遇到的问题 → 优化方案 → 最终版本。展示Prompt工程的实操能力。
5. **竞品分析：** 简要对比大众点评AI功能、小红书笔记推荐、小团助手，说明你的产品差异化在哪里。
6. **录屏视频：** 录制一个3-5分钟的Demo演示视频，放在项目README里。面试官可以先看视频，再决定是否深入。
