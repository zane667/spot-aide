## 0. 先把岗位听懂

JD 要的不是传统「只写 PRD 的产品经理」，也不是纯前端。关键词可以收成五句：

1. **0 到 1 验证**：AI 原生产品、Agent、内部效率工具，从概念做到能用。
2. **自己上手**：用 AI 工具做需求分析、原型、Prompt、流程搭建、效果验证。亮点写得很直白——团队不爱复杂 PRD，**希望你能自己写出 Demo，甚至做生产实验**。
3. **懂模型边界**：分析用户需求的同时，知道模型会幻觉、会圆场、会超时，交互必须可信。
4. **能跨角色说话**：和研发、算法、设计、运营把概念推到可落地版本。
5. **加分项对得上**：个人 AI 产品 / Agent / Workflow；会一点 Python、JavaScript、SQL；有作品集或可点开的 Demo。

探店参谋几乎是按这五条做的：自然语言进、结构化标签、规则闸门、评价可溯源、线上可演示。你的简历目前还停在「机器人运维 + 挑战杯 + 志愿队」，**探店参谋没有写进去**。面试官如果只看简历，会觉得你是「会原型的计算机学生」；看完 Demo，才会觉得你是 Builder。所以简历必须先改，再进面。

计算机专业是 JD 明确加分的背景。实习里做过 0 到 1 的 Web/App 和现场反馈迭代，和「从概念推到能用」同构。缺口是：本地生活业务体感、大规模评价数据、真正的 Agent 编排（多工具调用）。缺口不要藏，用探店参谋的边界讲清楚即可。

## 1. 简历改进意见（面试前尽量改完）

### 1.1 必须补上的一块：探店参谋作第一项目

建议插在实习之后、挑战杯之前，篇幅比挑战杯更长。推荐写法（可直接贴）：

**探店参谋 · 到店餐饮 AI 决策 Demo（个人项目）**  
产品设计与全栈实现 · 2026.08 – 2026.09  
线上：spot-aide.vercel.app

- 针对「评价看不完、约束对不齐」做需求驱动推荐：一句话解析为可改标签，从 50 家模拟商家、约 1266 条口语评价中匹配并生成最多 3 家，理由绑定评价原文。
- 设计并落地「模型当分析师、规则当闸门」：包间 / 安静 / 菜系 / 辣度冲突的店不允许靠文案圆进 Top 3；不够就少推，差距写入 gap。
- 独立完成 Prompt 迭代、zod 校验、匹配与硬拦截、DeepSeek JSON/SSE、Prisma + SQLite/Turso、Vercel 部署；用 Cursor 加速实现，决策和验收标准自己定。

数字只写仓库里站得住的：50 家、约 1266 条、正中负约 6:3:1、线上 URL。不要写「准确率 95%」「用户 1 万」这种没有的指标。

### 1.2 职业概述改一句，对准 JD

现在概述偏「产品设计 + 研发实习 + 会 Axure」。建议第一句改成 Builder 语言，例如：

计算机背景，能把模糊需求收成可验证的 AI Demo。常用 Cursor 独立完成需求拆解、Prompt、原型和上线；关注 LLM 幻觉与硬约束，不把聊天框当产品。对本地生活决策、Agent / Copilot 形态有实践（探店参谋）。

技能栏把 **Cursor、JavaScript/TypeScript、SQL、Prompt** 放到更显眼的位置。JD 点名 Python / JS / SQL：你有 SQL 和 Python 基础，探店参谋主体是 TypeScript，面试时说「这个项目用 TS + JS 全栈，SQL 用在 Prisma / SQLite / Turso」即可，不必假装主力是 Python。

### 1.3 实习和挑战杯怎么让路

实习保留「0 到 1、周期缩短 60%、现场 7 个高频问题」，用来证明你不是只会写 Demo 的学生。挑战杯压成 3 条：场景（老年数字沟通）、你负责产品、AI 辅助调研。志愿队用「用户研究」一句话带到「我习惯先看真实使用痛点」，不要在 Builder 面试里占五分钟。

### 1.4 投递材料清单

- 简历 PDF：探店参谋在第一项目，带可点击链接。
- 作品包：线上 Demo + 3 分钟脚本（已有 Word）+ 原型 HTML。
- 面试官若要文档：PRD / Prompt 迭代 / 数据设计 / 竞品分析都已成文，不要一上来甩五份，问到再给对应那份。

## 3. 项目开场 90 秒（必背）

面试官说「介绍一下探店参谋」时，按痛点 → 做法 → 边界 → 证据：

> 选餐厅时人不是缺店，是评价看不完，还要把包间、预算、小孩这些条件自己对上去。我没有再做一页列表，而是三步：说人话、读评价、给决策。
>
> 用户一句话进确认页，标签能改；规则按菜系预算包间等打分，安静油烟包间对不上的店先拿掉；模型只在可推荐集合里写理由和避坑，并引用评价原文。最多三家，不够就少推。还可以追问、切商户视角、点「我就去这家」记选择率。
>
> 评价库是按真实结构造的种子，没有接美团接口；解析、分析、推荐、写入选择是真的。线上可以演示。

然后停，等追问。不要自己把 Prompt 全文背出来。

## 4. 话术原则与避雷

### 4.1 要说的

- 「模型是分析师，不是聊天机器人。」
- 「LLM 擅长写理由，不擅长当闸门；闸门放规则层。」
- 「数据是模拟的，链路是真的。」
- 「我用 Cursor 提速，验收标准是我定的：JSON 过不了 zod 算失败。」
- 「小团做把事办成，我把办成之前的决策切深。」
- 「换真实评价源时，产品流程不用推倒。」

### 4.2 不要说的（避雷）

| 避雷 | 为什么 | 改成 |
| --- | --- | --- |
| 「我这个能替代小团 / 点评」 | 没有供给、交易、履约，说了会被判不懂业务 | 「不替代；只做决策这一刀」 |
| 「准确率很高 / 比 GPT 更好」 | 没有评测集上的准确率数字 | 「用固定测试句和守卫单测回归」 |
| 「50 家店是爬的点评」 | 不真实，也不合法 | 「种子脚本生成，结构对齐真实评价」 |
| 「全是我手写、没用 AI」 | 和 JD 相反，岗位就要你用 AI 做 Demo | 「用 Cursor 写代码，产品决策和闸门设计是我的」 |
| 「Agent 就是多轮聊天」 | 这个岗位的 Agent 含工具和流程 | 「主路径是工作流：解析→匹配→分析→推荐；追问是同一上下文的工具调用」 |
| 把思考过程、密钥、.env 投屏 | 泄密；思考模式你还关了 | 演示只走页面；被问模型时说 DeepSeek flash + JSON 模式 |
| 现场改 Prompt 炫技 | 超时、圆场、格式全可能翻车 | 用固定句；崩了按演示脚本的「卡住时」走 |
| 贬低实习「只是写界面」 | 实习里的 0 到 1 和现场迭代是加分 | 用实习证明你能和研发、现场一起收口 |

### 4.3 三个必须主动承认的边界

1. 没有真实 POI / 评价授权 / 余位 / 预订。
2. 没有行动代理（订位、支付、外呼）。
3. 没有登录体系和长期用户画像。

主动承认比被问穿好。紧接着补一句：「所以验收放在决策机制能不能演示，而不是 DAU。」

## 5. 面试情景怎么接

### 5.1 开场只有 10 分钟

先投屏或发链接 https://spot-aide.vercel.app（部分网络不稳，备手机流量）。按演示脚本走默认句，**不要现场发明第二句**。分析等待 15–30 秒时背「等待时说」：规则先拦、再读评价。来不及就保：输入带包间的需求、指理由+原文+避坑、「我就去这家」。追问和商户视角可口述。

### 5.2 面试官不看 Demo，只问概念

用 90 秒开场 + 一张嘴上的架构：「Next 页面 → parse/analyze/recommend API → DeepSeek + zod → matching/guard → Prisma」。然后问：「您更想听产品决策、Prompt，还是上线时的库？」把球踢回去，避免空讲。

### 5.3 面试官质疑「Cursor 写的，你懂吗」

不要辩护「每一行都是我想的」。说：

> 我会拆模块：Prompt 和 schema 必须我对齐，匹配权重和守卫是我定的规则，页面和胶水代码用 Cursor 加速。你随便点一个 API，我可以讲入参、zod、失败时前端怎样。我也写了匹配和选择率的单测。对我来说 Cursor 是 IDE，不是代答。

准备手写或口述：`pickRecommendable` 的分支（有可推荐 / 全军覆没兜底）、`parseNeedSchema` 为什么 `.strict()`。

### 5.4 面试官拿小团压你

> 小团已经到行动代理，那是美团有实时供给和履约才能做的。我没有这些接口，做订位是假的。我把五层里的决策辅助做成可演示：标签可改、硬拦截、gap、选择闭环。如果进组，下一步才是接真实评价和余位，把「选完」接到「订上」。

### 5.5 Demo 现场失败

| 现象 | 处理 |
| --- | --- |
| 解析失败 | 「再试一次」；或换「周末带父母吃饭，要安静有包间」 |
| 推荐转圈 | 不要刷新；讲硬拦截和「不编理由」，说明 30 秒超时、关了 thinking |
| 追问报错 | 跳到「我就去这家」，补一句追问也禁止编菜单 |
| vercel.app 打不开 | 手机流量；或改口「我用原型和高保真 HTML 把主路径过一遍」 |
| 推荐出了热闹店 | 不要狡辩。说「这正是守卫要拦的，我可以讲那一轮味正料理圆场，以及后来规则怎么改」——诚实比完美推荐加分 |

### 5.6 被问「为什么投美团 / 为什么这个岗」

不要答「大厂平台好」。对到 JD 和本地生活：

> 我关心的问题发生在到店决策。美团同时有 C 端小团和 B 端经营工具，评价和履约是一体的。Builder 岗明确要自己做 Demo、做生产实验，和我做探店参谋的方式一致。我想在有真实供给的地方，继续做「可信的决策交互」，而不是再做一个聊天套壳。

### 5.7 被问实习和探店参谋的关系

> 实习教我 0 到 1 和现场闭环：需求会变、终端会挂、要用反馈改产品。探店参谋把同一套用在 AI：模型会乱输出，就要 schema 和规则，而不是催模型「再认真一点」。

### 5.8 被问挑战杯 / 志愿队

各 30 秒。老年数字鸿沟 → 你做过调研和功能取舍；志愿队 → 你会盯真实使用（视频号、挂号）。然后拉回：「探店参谋里确认页可改标签、评价没写就明说，也是不替用户做假决定。」

## 6. 探店参谋可能被问到的题（含推荐答法）

### 6.1 产品与定位

**Q. 用户是谁？成功长什么样？**  
20–35 岁、今晚就要出门吃饭、约束多（小孩、包间、预算）。成功不是「理由漂亮」，是 3 分钟内能指出 1 家并愿意点「我就去这家」。次用户是演示用的店主视角，不单独注册。

**Q. 为什么不是 ChatGPT 对话框？**  
对话框会在库存外点名、编菜名。我把数据层卡死：先匹配库内店，再分析该店评价，追问禁止编菜单。产品形态是工作流加少量追问，不是开放域闲聊。

**Q. 为什么要确认页，不直接出推荐？**  
解析会错、会过度推断。确认页把纠错权给人，后续分析用改后的标签。这是承认模型边界，不是多余一步。JD 要的「可信交互」就在这里。

**Q. 为什么最多三家？为什么允许只出一家？**  
三家够对比、不制造新的信息过载。模型把「Top 3」当成必须凑满的配额时会圆场，所以改成 `min(3, 可推荐数)`。面试官若追问，举安静包间那句：最后只推白玉粤菜。

**Q. 选择率为什么权重只有 0.06？**  
避免「大家都点过」压过今晚的包间。先验来自均分、好评占比、负面标签；曝光和选择再用伪计数平滑，避免冷启动 0 除。

**Q. 你怎么评价这个 Demo 好不好？**  
四件事：需求有没有解对、理由能不能追溯到评价、硬需求会不会被圆进去、用户会不会做一个选择。没有线上 A/B，不冒充有。

**Q. 如果产品化，下一步做什么？**（必背）  
按依赖排序：真实评价与 POI → 时效和去重 → 余位/营业 → 再接到预订。产品流程（解析-确认-推荐-选择）可复用。不会一上来做推荐算法很大升级。

### 6.2 模型边界与 Prompt

**Q. 三条 Prompt 各自干什么？**  
解析：一句话 → 九个槽位 + inference。分析：一店多评 → 五维 1–10 + 三正三负。推荐：只在 recommendable 里写 reason/notes/gap。追问是第四条，口语、不输出 JSON。

**Q. Prompt 你是怎么迭代的？**（必背，约 2 分钟）  
最短 Prompt 先跑通。第一类问题是格式：不是 JSON、crowd 写成「4人」、空输入乱补标签 → 骨架写进 Prompt，zod `.strict()`，过不了算失败。第二类是推荐圆场：要安静还推热闹店，只改 Prompt 不够，因为「推荐三家」是配额 → 规则层先拿掉冲突店。每轮只改一类问题，固定测试句回归。

**Q. 为什么 JSON 模式还要在 Prompt 里写「只输出 JSON」？**  
DeepSeek 的 json_object 要求 Prompt 也声明；只开 API 可能拿到 `{advice: "..."}` 或空转。两边都要。

**Q. 为什么关掉 thinking？**  
Demo 要稳定 JSON 和及时 SSE。思考过程会占满约 30 秒超时，结果页像卡住。这是产品决策，不是模型越强越好。

**Q. 幻觉怎么防？**  
三层：Prompt 禁止编造并要求基于评价；zod 卡结构；追问评价没有就明说建议到店确认。推荐理由还要和风险信号对得上。不声称能彻底消灭幻觉。

### 6.3 硬需求与圆场（高频，必背故事）

**Q. 举一个你发现产品做错了的例子。**  
用例「周末带父母吃饭，要安静有包间」。第一轮南苑、西街进了 Top 3，西街自己写「热闹，父母要安静就不合适」却仍在列表里。第二轮味正料理写「油烟和吵」紧接着「仍能满足安静」。gap 比卡片诚实。根因是 Prompt 要凑满 3 家，且守卫只认「太吵」认不出「吵」「油烟」，环境分阈值偏低。后来规则拆 recommendable/ineligible，环境分低于 7 剔除，禁止圆场句。再测只出白玉粤菜。

这句话证明你做过效果验证，正好对 JD「效果验证」。

**Q. 规则和模型会不会打架？**  
会。标签可能写安静、中评写有点吵。匹配看标签，分析看正文，守卫两头都读。这是故意保留的脏数据，接近真实标签云。

### 6.4 数据

**Q. 数据是假的，有什么说服力？**  
校招 Demo 接不了点评接口。种子按真实结构造：上海商圈、口语、约 18% 错字、按店配 6:3:1，每家至少一条差评。说服力在机制：抽取、拦截、溯源、选择闭环。换真数据时重跑先验即可。

**Q. 为什么正负 6:3:1？**  
好评墙抽不出避坑；全差评默认句推不出能上台的粤菜；中评里的「有点吵」才是安静拦截的主力。比例按店配，不是全局打完再随机分。

**Q. 标签和正文为什么不一致？**  
标签给规则打分，正文给模型。随机补丁模拟脏标签。产品选择双读，而不是把种子做成完美对齐的假世界。

### 6.5 竞品

用竞品分析那三句就够：点评把评价变好用、人还在列表里；小红书做想去；小团做办成；我做该不该去、凭什么，而且可拒绝。商户视角是 CatPaw 的切片，不是商家工作台。

### 6.6 工程与协作

**Q. 技术栈为什么这么选？**  
要尽快可部署：Next 全栈、Vercel、Prisma。模型用 DeepSeek 的 JSON 和价格适合 Demo。线上 Vercel 文件系统只读，所以生产库换 Turso。没有为了简历去上微服务。

**Q. 你和算法同学怎么协作？**（JD 有跨角色）  
我会先把接口契约讲清：parse 的 JSON 键、分析的五维英文键、推荐的 merchant 必须原名。算法若换模型，只要还过同一份 zod，产品不用改。守卫是业务规则，应由产品和算法一起签，而不是埋在 Prompt 里。

**Q. 如果让你一周接真实评价，风险在哪？**  
授权与隐私、时效、刷评、AIGC 假评（点评也在治）、字段对不齐。产品上先保硬拦截和溯源，再谈个性化。

**Q. Token 谁付钱？现场会不会被刷？**  
密钥在服务端。打开首页不调模型。链接公开，走完推荐会消耗额度。面试若追问：会考虑演示环境限流或关写路径，这是我知道的产品风险。

## 7. 技术栈与实现细节（深挖备用）

面试官若是偏技术的 Builder / 研发，从这条链路讲，不要背依赖表。

### 7.1 总览

| 层 | 实现 | 面试怎么说 |
| --- | --- | --- |
| 前端 | Next.js 16 App Router、React 19、Tailwind 4 | 页面：首页 / confirm / results / thanks；移动端、骨架、空态错误态 |
| API | `app/api/parse|analyze|recommend|insight|merchants|session|choice` | Route Handler；recommend 用 SSE |
| 模型 | DeepSeek `deepseek-v4-flash`，`lib/deepseek.ts` 统一封装 | JSON 模式；thinking 关闭；30 秒超时 |
| 校验 | zod，`.strict()` | 多字段直接失败，不静默丢弃 |
| 匹配 | `lib/matching.ts` 权重：菜系 0.28、预算 0.22、设施 0.12、口味 0.12、位置 0.13、氛围 0.08、场景 0.05、选择率 0.06 | 硬未命中给极低分，避免挤进 Top 5 |
| 闸门 | `lib/recommend-guard.ts` | 安静/油烟/环境分&lt;7、包间、菜系、辣度 |
| 数据 | Prisma 6；本地 SQLite；线上 Turso（libSQL adapter） | 商家、评价、标签、场次、曝光、选择 |
| 部署 | Vercel 项目 spot-aide | 环境变量：DeepSeek + Turso |

业务代码禁止直连 DeepSeek，一律走封装。Prompt 用 `fillPrompt`，缺参或多余参抛错，占位符不能漏进模型。

### 7.2 主路径实现

1. **解析 `POST /api/parse`**：query 最长 500 字 → `PARSE_NEED_SYSTEM` → `chatJSON` → `parseNeedSchema`。前端确认页可改九个槽位。
2. **分析 `POST /api/analyze`**：全库商家，每家最近 20 条评价；`rankMerchants` 截 Top 5（`CANDIDATE_LIMIT=5`）；对每家调分析 Prompt。评价不足 5 条 `dataInsufficient`。失败则该店 analysis 为空，不填假分。
3. **推荐 `POST /api/recommend`**：`pickRecommendable` 拆集合；SSE 流式输出；拼完再过 `recommendResultSchema`（1–3 条）。`merchant` 必须是候选原名。
4. **场次 `POST /api/session`**：记下本轮曝光。
5. **选择 `POST /api/choice`**：每场次唯一，来源 card 或 search。
6. **追问 / 洞察**：同一批 needs + candidates + 已有推荐；洞察复用分析 Prompt，换展示角色。

### 7.3 选择率公式（可能被白板）

先验：`0.45×(均分/5) + 0.35×好评占比 + 0.2×(1−负面标签占比)`，不足 5 条再 ×0.7，夹在 0.05–0.95。  
展示：`(选择次数 + 先验×10) / (曝光 + 10)`。10 是伪计数，避免 0 曝光时乱跳。

### 7.4 测试怎么说

- `scripts/test-prompts.ts`：20 条需求（常规/模糊/空/极端预算）。
- `scripts/test-pipeline.ts`：全链路。
- `lib/recommend-guard.test.ts`：吵、油烟、环境分 6、包间、辣度。
- `lib/matching.test.ts`、`lib/selection-rate.test.ts`。

可以说「我不是只看一两次生成好不好，而是把圆场做成回归」。

### 7.5 你不必装懂的

没做：向量检索、微调、多 Agent 编排框架、真实推荐系统特征平台。被问「为什么不用 RAG」：50 家店全量打分足够；真上成千万评价再考虑检索。被问「为什么不用 LangChain」：链路短、契约清，自己封装更可控。

## 8. 做过时遇到的问题，以及你怎么处理（必背四段）

用「现象 → 判断 → 动作 → 结果」讲，像复盘不是诉苦。

**1. 模型输出不能进产品。**  
现象：markdown 围栏、`crowd: "4人"`、空串「吃」仍补预算。  
判断：不是模型笨，是契约没锁。  
动作：Prompt 内嵌 JSON 骨架；zod strict；空输入除 inference 全 null。  
结果：解析失败即失败，确认页不再出现用户没说过的一排标签。

**2. 推荐会圆场。**  
现象见第 6.3 节味正 / 西街。  
判断：只改 Prompt 不够，上下文里还有冲突店，配额是 3。  
动作：规则先拆集合；ineligible 只留店名和原因；Prompt 禁止「虽然…仍能满足」。  
结果：安静包间句只出 1 家；守卫有单测。

**3. 思考模式把 Demo 拖死。**  
现象：推荐超过 30 秒，页面像卡死。  
判断：产品要的是正文和 JSON，不是思维链。  
动作：请求里 `thinking: disabled`；进度文案轮播降低「死机感」。  
结果：等待可预期；面试演示用这段讲规则而不是干等。

**4. 线上不能写 SQLite。**  
现象：Vercel 只读文件系统，记场次、记选择会失败。  
判断：本地和线上存储必须分模式，产品主路径不能静默失败。  
动作：Prisma 双模式，生产走 Turso；无写库时要有说明，不能让「我就去这家」无反馈。  
结果：选择能落库，选择率能更新。

另外可提一句：分析 Prompt 曾输出中文键或一次多家店，后来锁英文扁平键、写明「同一家店」。匹配高分但正文喊吵，促使守卫读分析文本而不只读标签。

困难里不要说「我不会写 Next 所以全交给 Cursor」。可以说「全栈细节用 AI 补，产品契约和闸门我盯住」。这和 JD 完全同向。

## 9. 反问环节：问什么显得是 Builder

反问目的：证明你想清楚进组后怎么干活，不是套近乎。准备 3 个，现场问 2 个。不要问薪资、加班、几轮 HC。

**优先问（更会被看好）：**

1. **验收怎么算。** 「组里一个 AI 功能从想法到可灰度，通常看哪些信号？是任务完成率、人工满意度，还是会看硬需求冲突率这类过程指标？我 Demo 里用『会不会圆场』和『会不会点去这家』，想对一下你们线上怎么验。」
2. **Builder 和产品 / 算法怎么切。** 「JD 写自己写 Demo、少写复杂 PRD。实际和产品经理、算法的分工是谁定问题、谁定闸门规则、谁对幻觉负责？我想知道进组第一季度我该独立交付的是原型还是已经能进主站的实验。」
3. **本地生活决策的下一段。** 「小团已经在行动代理。决策辅助这一层，评价冲突、余位、硬约束，你们现在最痛的是哪一段？我的作品停在决策，想判断我该补真实数据，还是补工具调用。」

**可以问、但放后面：**

- 「新同学第一个月会跟哪类需求，偏 C 端对话还是内部效率 Agent？」
- 「生产实验失败时，你们更倾向收紧规则，还是换模型？」

**不要问：**

- 「你们用哪个大模型」（像科普）
- 「加班多吗」
- 「我没有本地生活实习会不会很亏」（把不确定甩给对方）
- 「探店参谋能不能直接上美团」（天真）

收尾一句：

> 如果有机会，我希望第一段就做「能上线验证的小闭环」，继续用规则+模型的方式处理可信推荐，而不是先画很久的 PRD。
